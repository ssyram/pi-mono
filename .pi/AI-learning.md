# AI 学习原则

## 新清单格式化不应扩张成历史清单维护

- **来源**：用户追问 F/F' 关系后指出，只需在本轮机械清单 F' 首次生成时压缩；上一轮完整摘要沿原流程交给模型，无需拆出旧 F 再格式化，也不应虚构跨轮 union 或智能去重。
- **原则**：表示变换放在值的权威生成点。若目标只是缩短新生成的机械清单，就在生成 F' 时格式化；不要把优化扩展为历史摘要迁移、旧 suffix 显示投影或跨轮集合维护。既有解析边界即使可复用，也不能反证新增处理必要。
- **适用**：compaction 文件清单、滚动摘要、派生表示和历史迁移设计。

## 路径前缀合并应直接表达目录树结构

- **来源**：用户否定仅合并相邻同父目录路径的实现，明确要求按路径段建立前缀树，以 A/{B/{C,D},E/F} 表达嵌套共享前缀，不同根分行。
- **原则**：目标是消除共享路径前缀时，直接建模路径树，不用局部相邻分组替代完整需求。根级文件是普通叶节点，不应使其他分支失去压缩。证明局部算法满足自设合同，不能替代确认该合同覆盖用户目标。
- **适用**：compaction 路径清单、目录前缀压缩和表示算法选型。

## Compaction 清单未缩短须先检查 formatter 的回退粒度

- **来源**：用户指出 live compact 的 modified-files 已合并而 read-files 未合并；此前错误归因为旧摘要正文，源码实际把无目录前缀的 biome.json/package.json 判为不可处理并令整节回退。
- **原则**：可见格式只证明输出形态，不能证明其由模型复制还是机械追加。先检查实际输入项、判定条件和回退范围；不需要合并的单个路径不应无依据地阻止其他可合并路径。结构性不增长证明不等于常见输入上的压缩目标已实现。
- **适用**：compaction 文件清单、批量格式化、保守回退和 live 结果归因。

## 多账号插件：区分 provider 名称、运行时实例与凭据槽

- **来源**：用户要求从多 Codex / Z.ai 账号切换追问合理配置边界；此前方案把 `compat.getProviders()` 误当成完整 provider 列表。
- **原则**：`getBuiltinProviders()` 返回目录键名，`builtinProviders()` 才构造完整 Provider。不得由相似函数名推断返回值或宣称 spread 改 id 即可复用；派生模型归属、认证键、刷新与过滤的身份绑定须各自成立。账号声明与官方模型元数据应分离，避免手抄元数据落到默认输出/思考能力配置。配置实例、发现外部账号和共享外部凭据的生命周期是不同责任。
- **适用**：Pi provider 别名、OAuth 多账号、模型目录复用及外部 CLI 账号接入。

## 2026-09-14 — 获得本地执行授权后立即继续

- **来源**：skill-ref 调查中子代理因服务过载失败；用户明确要求不要使用 subagents，并指出不应停止调查。
- **原则**：受治理流程约束的子代理失败时不得静默切换执行模式；但用户明确授权改用本地工具后，应立即沿原目标继续，不再把已解除的执行方式限制当作任务阻塞。
- **适用**：子代理、外部 CLI、远程服务等执行通道失败后的同任务续办。

## 2026-09-15 — 内部引用标记不得进入用户可见摘要

- **来源**：Impression 引用格式讨论中，错误建议把转义后的内部 `@!N@` 显示成 Related parts 的位置标签；用户明确禁止泄漏内部编号。
- **原则**：区分模型草稿协议与最终用户界面。内部引用 ID 只用于展开，不是稳定来源位置；最终摘要若需位置，只输出从源块元数据计算的自然坐标。设计示例必须同时检查“模型应输出什么”和“展开后用户会看到什么”。
- **适用**：引用展开、压缩摘要、source map、位置标签及其他内部句柄替换协议。

## 2026-09-15 — 内部编号禁显规则必须区分正常输出与诊断

- **来源**：用户进一步裁决：正常 Related parts 绝不能显示内部引用编号，但 unresolved 占位符允许携带内部表达式，便于 recall 后排查来源。
- **原则**：正常成功路径只显示展开原文或自然坐标；失败路径使用明确的中性诊断，并可在诊断括号内保留内部表达式。不要把“禁止把内部 ID 当用户界面”错误扩大成“任何诊断都不得包含内部 ID”。
- **适用**：引用协议、位置投影、错误占位符、召回缓存及面向用户的内部句柄显示。

## 2026-09-15 — 缓存 prompt 的插件更新后以 reload 划分验收边界

- **来源**：Impression prompt 更新后，reload 前的长生命周期实例出现新旧摘要格式交替。
- **原则**：磁盘上的 prompt 已更新，不代表所有实例都已清空各自的 prompt cache；reload 前偶发出现新格式只能算旁证，不能替代 reload 后的受控 live test。
- **适用**：缓存 prompt、模板或配置的插件热更新与运行时验收。

## 2026-09-15 — “提交全部未提交内容”仍需先量化异常范围

- **来源**：Impression 提交前虽说明会纳入全部未提交内容，但未在最终确认前明确给出 319 个文件、运行 transcript 与历史研究语料的数量，导致提交规模超出用户直觉。
- **原则**：当提交范围包含本任务之前的未提交内容时，必须在执行前报告文件总数、主要目录、生成物/运行产物数量和体积；用户确认的是量化后的集合，而不是抽象的“全部”。
- **适用**：脏工作区、嵌套仓库、多会话并发以及包含日志、transcript、audit artifacts 的批量提交。

## 2026-09-15 — 计划先交付人话骨架

- **来源**：OMP compact 方案已被要求“长话短说，说人话”。
- **原则**：用户把控方向时，先说明改什么、为什么、失败怎么办和分几步；文件、签名、证明与完整测试矩阵只在需要落地或用户追问时展开。
- **适用**：架构计划、阶段方案和批准前设计说明。

## 2026-09-15 — Compact 原文候选池按轮次滚动，不回扫整条 branch

- **来源**：用户纠正 OMP compact 设计：应提供“上次 compact 里保留的 + 这次即将被压掉的”用户原文，而非当前 branch 的整个历史损失前缀。
- **原则**：每轮候选池等于上一轮保留下来的原文与本轮新进入压缩区间的 user messages；模型重新选择后，未再次保留的候选自然淘汰。不要把“历史仍可读取”擅自扩大成“每轮都重新开放全部历史”。
- **适用**：递归摘要、滚动 checkpoint、选择式原文保留和跨轮 source reference。

## 2026-09-15 — Compact 引用是自由摘要的可选快捷方式

- **来源**：用户明确 compact 仍允许像现在一样自由写定制文本，引用只用于直接选择原文；旧 compact 可通过 summary 与 branch 原文的 matching 恢复候选。
- **原则**：不要把引用协议变成结构化摘要的强制输出。引用是保留现有文字的快捷方式，不限制自由写作。此前的精确匹配迁移只适用于已放弃的“恢复历史消息来源”方案；当前直接索引摘要正文，不需要任何迁移匹配。
- **适用**：滚动摘要迁移、可选 source reference、旧数据兼容和渐进式协议升级。

## 2026-09-15 — Compact 选择状态必须由 session 持有

- **来源**：用户指出插件模块可能被多个 session 共用，并追问上一轮选择的用户信息如何保存；进一步追问每轮全历史 exact matching 的复杂度。
- **原则**：禁止用插件模块级可变数组、Map 或“上一次 compact”变量保存选择。是否持久化取决于真实跨轮义务：如果下一轮只需引用已保存摘要的文字，直接重建调用内索引即可，不应为旧方案遗留的来源追踪继续保存 `selectedEntryIds` 或执行 matching。
- **适用**：多 session extension、递归 compaction、分支状态、旧数据迁移和跨轮引用。

## 2026-09-15 — Compact 所有已存在原文都应原位标号

- **来源**：用户先纠正本轮 user messages 不应复制到 additional block，后进一步指出上一轮选择的原文已经存在于 `previousSummary`，再追加 old/potential block 仍然重复。
- **原则**：当前 loss-region user messages 在既有 conversation 位置内联标号；旧摘要正文直接在 `previousSummary` 中分块标号，不再寻找历史原文 occurrence。不得为已存在的文字再复制 source block，也不得新增 `current_history` wrapper、额外 LLM message 或平行上下文空间。
- **适用**：滚动 compaction prompt、previous-summary 标注、上下文预算和引用协议。

## 2026-09-17 — 区分文字保留与历史来源恢复

- **来源**：用户将 compact 引用范围收敛为旧摘要正文和本轮待压缩的纯文本用户消息；选择直接重建临时索引，不再追踪历史消息 ID。
- **原则**：如果目标是准确复用当前已存在的文字，不要擅自附加历史来源恢复义务。只有后续消费者确实需要来源身份时，才引入持久化 ID、原文匹配或迁移机制；索引可引用性不等于用户作者身份或事实真实性。
- **适用**：滚动摘要、引用展开、来源追踪、缓存和派生状态的持久化设计。

## 2026-09-17 — 可见范围与可引用范围分别定义

- **来源**：用户要求 AI 发言、工具结果和文件清单不编号，但仍保留现有 compact 上下文。
- **原则**：不给某类内容提供引用快捷方式，不等于把它从模型输入中删除；同时，无编号内容仍需避免被字面协议标记误识别。范围筛选、内容展示和转义承担不同义务，不可互相替代。
- **适用**：混合来源 prompt、局部索引、引用协议与上下文裁剪。

## 2026-09-17 — 分隔符归属由语法决定，不由查询结果决定

- **来源**：Compact codec 实现阶段用 `@!1@!` 暴露闭合符与下一前缀重同步的冲突；直接回归同时覆盖有效 ID、未知 ID、无效范围和终止标记后跟普通感叹号。
- **原则**：先按语法确定一个表达式占用的输入区间，再做来源查询和语义判定。查询成功与否不应反向改变已经完整表达式的闭合符归属；只有语法不完整时才使用恢复规则。否则同一文本会因外部状态变化而吞掉后续普通内容。
- **适用**：引用展开、模板插值、标记解析与带容错恢复的文本协议。

## 2026-09-17 — 装饰文本必须避开既有序列化的语义边界

- **来源**：Pi 在序列化时截断工具结果并格式化工具参数；提前转义原始内容会改变截断位置和 JSON 文本。新实现按原始角色判定资格，但在官方序列化之后才做展示转义和标注，并以实际源码的批量/逐条输出一致性测试约束适配器。
- **原则**：新增标签或转义不一定是无害的展示变换。若上游还会执行截断、编码、角色投影等有损或语义变换，应分别确定身份判定和展示装饰的正确时点；通过可组合性证据保留现有语义，而不是为了接入方便重写原生格式。
- **适用**：上下文标注、日志装饰、序列化适配、内容裁剪与引用显示。

## 2026-09-17 — JSON 边界必须显式处理可选字段缺失

- **来源**：编排工作流把子任务结果中缺失的 `outputPathMapping` 重建为值为 `undefined` 的字段，导致两个侦察完成后 `emit` 失败；改为合法的 `null`，并针对缺字段结果执行回归。
- **原则**：一个对象曾经过 JSON 边界，不代表从其可选属性重新构造的对象仍是合法 JSON。跨边界投影应明确省略或规范化缺失值；静态脚本校验不能替代真实返回形状的直接测试。恢复时复用已完成工件，不重跑成功任务。
- **适用**：任务编排、消息总线、工具结果、事件上报与跨进程数据接口。

## 2026-09-17 — 最小接入点靠完整调用内封装，不靠压行

- **来源**：用户要求把 compact 接入后的必要逻辑提前放进基础设施，尽量让每个接入点不超过三行。实现把 prompt 准备、ON/OFF 判定和摘要收尾放进同一次请求对象，后续 handler 仅需两行准备、一行收尾。
- **原则**：减少接入点时，把共享一次调用状态的完整义务放到拥有该状态的模块，由调用者保留模型调用、状态清理和最终持久化。不得把多条语句挤成一行、用全局变量传递模式、隐藏副作用或省略旧块删除来制造“小改动”。对外分别说明新增调用行数与完整 diff 范围。
- **适用**：插件接线、中间件、请求/响应转换及可选功能集成。

## 2026-09-17 — 测试入口失败不能升格为安装包失败

- **来源**：新 facade 的未隔离 tsx 测试通过根配置源码别名加载公共聚合入口，触发缺失模型目录；用两个明确的测试加载重定向后，真实序列化/估算代码的源码测试通过。
- **原则**：故障与通过结论都绑定实际加载路径。源码别名环境的聚合入口失败，不证明独立安装包故障；隔离无关依赖后源码测试通过，也不证明部署入口正常。测试隔离只能缩小加载边界，不能替换被测算法或模拟未执行的成功。
- **适用**：monorepo、源码别名、模块加载器、包发布验收与测试环境隔离。

## 2026-09-17 — 回退路径必须保留可区分的失败原因

- **来源**：用户实测 compact 得到 `unusable summary; using built-in` 后要求立即回退。新封装把空草稿、空展开结果、展开后超限都返回空字符串；现有记录又没有失败响应，无法确定实际触发项。
- **原则**：保持原调用接口简短，不能以丢失拒绝原因和关键指标为代价。多个有不同修复方向的分支共用回退行为时，至少保留原因与必要的非敏感长度/预算/停止原因；不要默认某个 transcript 插件存在或已记录返回值。证明拒绝分支会执行，不等于证明其条件适合真实使用场景，也不能用于认定某次失败根因。
- **适用**：compact、引用展开、输入/输出限制、降级链和模型调用诊断。

## 2026-09-17 — 索引接入不应附带新的接受/拒绝策略

- **来源**：用户否定 compact 引用封装中的额外输入估算和展开后预算检查，明确要求“原来咋整就咋整”。本次删除这些门槛，保留原有模型生成 `maxTokens` 和空正文处理，并保持入口停用。
- **原则**：引用标注/还原与输入输出是否可接受是两项不同义务。模型生成预算限制的是模型实际生成的文字，不能因复用同一个 `maxTokens` 字段就顺手变成引用展开后正文的硬上限。若没有独立的行为约束依据，接入只做表示转换，不附加估算、截断、重试或拒绝；删除门槛也不能偷偷换成另一种门槛。
- **适用**：compact、引用替换、序列化适配、解压/展开与原流程的最小侵入集成。

## 2026-09-17 — 已备好基础设施的接线不能重新扩成大工程

- **来源**：用户追问 compact 接入明明只有一两处调用，为什么耗时很长、产生许多外围改动。实际调用点只有两行准备、一行收尾，耗时却扩展到测试加载适配、源码/构建 SDK 类型混用和重复文档维护，且附带了后来被否定的预算策略。
- **原则**：调用处行数不代表总实现量，必须如实区分；但基础设施已就绪后的接入应只包含约定接线、旧重复代码移除和直接针对行为的必要回归。不得重新加入行为策略，也不得把辅助测试/文档/编排成本无界扩张。测试适配成本明显超过接线时应及时说明障碍并收敛最小边界，而不是以流程完备替代完成任务。
- **适用**：成熟基础设施的运行接入、小范围集成、测试环境适配与交付成本控制。

## 2026-09-17 — 引用不抛错不等于不回退或没有资源放大

- **来源**：用户要求 compact 引用接入自身不失败；独立 Hoare 推导和原生 preparation 探针确认，无效语法产生诊断，但合法空切片或终止符可使非空草稿展开为空，进入原有空摘要回退。重复短引用还可放大输出分配。
- **原则**：分别陈述语法不抛错、摘要有效性和资源条件。不能把返回一条非空提示冒充有效摘要来“修好”回退，也不能把生成长度当作展开内存上界。没有可达代码缺陷时不为制造改动而改；修正文档中的过期状态，并明确保留的语义与资源边界。
- **适用**：compact、引用替换、模板展开及带降级路径的数据变换。

## 2026-09-18 — 批量任务按约定保留部分效果，不套用事务默认值

- **来源**：用户明确修正批量创建方案：环边跳过但任务照常创建，被阻塞的启动请求只是不启动，并报告实际效果；终态依赖仍成功添加并说明已经满足。随后强调基础设施和运行接入必须分别批准。
- **原则**：批量语义由用户目标决定，不能默认整批回滚。尽力执行时先创建有效项，再按确定顺序处理依赖，最后尝试启动；逐项说明已生效与未生效部分，不将部分成功包装成全失败，也不将坏边静默丢弃。该容错不自动推广到单条操作或底层 I/O 故障。基础设施的实现授权不越过尚未批准的运行接口。
- **适用**：任务批量创建、依赖图更新、带部分成功结果的操作及分阶段插件接入。

## 2026-09-18 — 后台进度不能以空回应制造停工观感

- **来源**：任务基础设施子代理回报测试与接入方案进度后，主会话被唤醒显示 Thinking，却以空回应结束；用户无法判断是在继续、等待还是停工。
- **原则**：区分主会话回合结束与后台任务结束。在阶段性进度处简短交代实际剩余工作；用户追问时查一次真实运行状态，不以猜测解释停顿。必需实现和直接检查完成后立即收敛交付，不为整理报告追加测试或审查。
- **适用**：异步子代理、后台实现与分阶段交付。

## 2026-09-18 — 任务异常隔离必须区分宿主路径与提交阶段

- **来源**：用户要求任务系统普通故障不能拖垮 harness；获授权的独立 Hoare 分析指出，原生工具与门禁已有异常兜底，但补全失败可污染后续请求链。实际 built Editor 隔离探针中，两次请求失败而 provider 只被调用一次；原生持久化探针也显示日志可能先变更后抛错。
- **原则**：以真实调用边界判断异常影响，不把 helper 抛错直接等同于 harness 崩溃，也不把宿主兜底当作插件已返回明确失败。补全必须在捕获范围内 await 委托请求，并验证失败后的下一次调用仍可运行；失败退路不得重用已失败依赖。任务失败保留旧控制器记录和编号预留，但原生日志是否写入须诚实报告；持久化前准备好安装副本，成功返回后只发布该副本，避免在提交之后再做可失败的复制或格式化；提交后展示失败不能宣称修改已回滚。内部解析器在调用方完整承接时可以继续抛错，不逐函数机械套 catch。
- **适用**：OMP 任务控制器、工具门禁、人工命令、补全回调及其未来运行接入。

## 2026-09-18 — 共享定义与会话执行关系必须分层

- **来源**：Loop 2.0 讨论中，用户区分了 global/workspace 中“可注册的任务定义”和当前 session 的 active 任务，并要求共享定义不得因读取而复制成 session item。
- **原则**：存储作用域、注册关系和执行状态是三个不同维度。共享层只保存可复用定义；session 通过显式注册持有引用及独立进度；`list` 展示当前 session 已启用执行，`available` 只查询尚可注册定义且不得产生副作用。共享权限必须由用户命令的结构边界授予，不能把 AI 提供的 `scope` 参数当成授权。
- **适用**：定时任务、订阅、共享模板、跨会话资源和任何“定义可共享但执行状态私有”的插件设计。

## 2026-09-18 — 隔离 smoke test 必须同时隔离状态根并重建真实模型上下文

- **来源**：Loop 2.0 用临时 Pi session 验证时，将 cwd、session dir、workspace/global store 和 locks 全部放入同一临时根；完整 JSONL 含任务 custom entries，但 Pi `buildSessionContext()` 重建结果不含隐藏任务和未注册共享定义。
- **原则**：真实宿主测试不能只换 session ID；所有持久化根和执行锁都要显式重定向，并在测试后整体删除。判断 AI 可见性不能以“内容是否存在于 transcript/JSONL”为准，必须使用宿主的 context builder 或等价的一手请求证据；custom entry 的可持久化与模型可见性是两个维度。
- **适用**：Pi 扩展 smoke test、session 状态、LLM 上下文隔离、临时 global/workspace 数据和测试清理。

## 2026-09-18 — 共享任务的取消、删除与强删必须分开

- **来源**：用户要求普通 stop 只取消自己的 registration，普通 delete 只能在没有其他注册者时删除共享定义，而用户 `delete --force` 可令全部注册失效；AI 不得 force。
- **原则**：取消改变当前 session 的执行关系；删除改变共享定义所有权；强删撤销所有 session 的共享执行资格，三者不能复用一个模糊操作。跨 session 强删应在共享索引中立即失效，并让离线 session 下次启动时清理本地引用，不能宣称原子改写其他 session JSONL。Catalog 不可读也不能被当作已强删，否则 reconciliation 会误删仍有效的本地状态。
- **适用**：共享定时任务、订阅关系、协作资源删除、离线客户端和跨会话权限撤销。

## 2026-09-18 — 接入后文档终态必须逐文件核读，不能采信实现者自述

- **来源**：Loop 2.0 转正提交后用户追问文档是否全部同步；实际发现 architecture/detailed-design 仍写着“future 自动补全未注册”、decisions.md 的 D6 与 non-decisions 已被推翻但未标注、旧 v1 设计文档无取代标注。这些内容曾被子代理自述为“已更新”。
- **原则**：委托实现后的交付清单里，“文档已同步”是一种主张而非证据；接入、删除、重构这类改变时态的动作会让文档中的 future/not wired/core-only 措辞整体翻转含义。核验必须亲自逐文件读终态，重点扫时态标记、决策状态和 superseded 标注；废弃决策按规范标注取代而非删除或改写。
- **适用**：委托实现后的文档验收、分阶段接入、方案转正、任何含“将来/未来/尚未”描写的文档交接。

## 2026-09-21 — 基础设施验收与行为接入必须是两个授权门

- **来源**：用户明确要求先完成 compaction 路径压缩基础设施并执行 Hoare 推理，但不得提交、不得接入当前行为；交付 review 结果和最小接入代码方案后，只有再次同意才允许接线并执行行为测试。
- **原则**：第一阶段只能落地未被运行入口引用的纯模块、直接源级测试和证明材料，并用入口哈希或 import 图证明现有行为未变。未来接入补丁可以预先精确生成和检查，但不能应用，也不能用“基础设施已经测试”替代接入后的行为回归。第二阶段必须重新取得授权，才修改入口并运行离线行为测试；若用户保留 reload/live 验收，接入者不得代为 reload 或调用真实 provider，须把离线通过与 live 待验分开交付。
- **适用**：分阶段 runtime 接入、provider/compaction 行为变更、feature flag 启用及任何“先构建后上线”的插件工作。

## 2026-09-21 — 组合任务动作只编排既有原子动作

- **来源**：`done + startNext` 设计中，用户要求直接复用现有 `start` 基础设施，并质疑非空数组、去重和独立启动逻辑是否必要。
- **原则**：便利型组合 action 只负责输入归一化、按序调用既有原子 action、汇总原子结果；不得复制其状态校验，也不得无依据新增非空、去重或事务规则。复合动作若保留主动作的部分效果，必须逐项返回后续动作错误，不能因主动作成功而静默吞掉 handoff 失败。
- **适用**：任务生命周期组合、批量快捷参数、已有原子状态转换之上的 API 编排。

## 2026-09-22 — 基础设施故障只报告任务影响

- **来源**：`startNext` 委派审查连续遇到 staged 验收条件和模型标识校验故障时，进度回复直接暴露了 `thinking`、模型 ID 和重试协议，用户无法判断这些术语与功能任务的关系。
- **原则**：面向用户报告执行基础设施故障时，先说明实际任务哪一步完成、哪一步未完成、代码是否受影响以及下一步；内部模型标签、调度字段和协议细节只有在需要用户选择配置或授权时才展开。自动重试不得形成无法理解的连续状态噪声，出现重复基础设施故障时应收敛或请求决策。
- **适用**：子代理、模型路由、验收 gate、后台任务与异步进度沟通。
