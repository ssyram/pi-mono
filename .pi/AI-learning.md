# AI 学习原则

## 2026-11-24 — gitignored 生成数据是本地构建前提，合并后必须重新生成

- **来源**：upstream 合并后 npm run check 报 packages/ai/test 引用 gpt-6.2-sol 等但类型里没有；重新跑 catalog 生成器后 tsc 直接通过，且 git 无任何变更。
- **原则**：先分清“已提交源码不一致”和“gitignored 本地生成物过期”。models.generated.ts/*.models.ts 只是类型包装，真正数据在 packages/ai/src/providers/data/*.json（gitignored，由 `cd packages/ai && npm run generate-models` 从 models.dev/openrouter/vercel 拉取）。合并官方代码后必须重新生成，不能看到类型错就手改 .ts。
- **边界**：Node fetch（undici）不读 http_proxy 环境变量，需 `NODE_USE_ENV_PROXY=1` 才走代理，否则 models.dev 连接超时；这不是代码 bug。生成器要联网，用后台脚本+足够超时跑，脚本里 `dirname $0` 相对路径要按脚本实际所在目录算。

## 2026-11-11 — 请求取消不能向未监听 error 的隧道连接注入异常

- **来源**：用户报告 pi-cc 运行时按 Esc 导致 Pi 进程崩溃；本地 HTTPS/CONNECT 取消测试复现未捕获 Claude Code request aborted。
- **原则**：正常取消由 AbortSignal 表达，连接清理使用无错误 destroy，不能对原始代理 socket 注入自定义 Error 而触发宿主未捕获事件。CONNECT 建立阶段也必须接收取消信号，等待完成后再次检查是否已取消，避免中断后继续发上游请求。确认实际安装路径，修复 fork 的同时同步当前加载副本。
- **边界**：取消回归覆盖等待头、流式响应、等待 CONNECT 及下一轮可用；真实验收是在 tmux 中 Haiku 流式输出时 Esc 出现 Operation aborted，随后同一会话返回 recovered。不是以进程仍存在或界面停止刷新冒充可恢复。

## 2026-11-11 — 上游参考更新与插件运行故障分开处理

- **来源**：用户明确要求直接合并官方 main，插件目录及 AGENTS 本地新增规则是保留边界，并报告 Boulder hook failed。
- **原则**：合并前单独保存本会话暂存补丁，合并不夹带未完成插件提交，随后恢复暂存；官方参考数据冲突按用户决定采用上游。第三方接口变化要用真实模块回归复现，不能只看调度器的泛化 warning：本次是 snapshotBackgroundWork 从单身份参数变为身份数组，旧字符串调用触发 map 异常。
- **边界**：源码合并不代表正在运行的 Pi 已更新，也不代表依赖和全仓检查通过；Boulder 39 项测试只证明本次调用与调度回归，既有检查阻塞单列。

## 2026-11-11 — 蒸馏历史不是可直接重放的完整工具事务

- **来源**：用户实测 CC 蒸馏报 400，当前 tool_use 缺少紧邻 tool_result；此前仅覆盖 provider 路由的假模型测试未验证工具事务结构。
- **原则**：tool_result hook 内的会话历史可能已有当前调用但尚无当前结果，并行工具也可能只有部分结果。无工具蒸馏应把历史调用与结果作为带名称、ID、参数和原内容的参考数据，不原样重放为工具协议，也不伪造成功结果。回归必须覆盖未完成调用、部分并行结果、孤立结果和 recall。
- **边界**：假 provider 的成功只证明其实际检查的条件；未检查原生协议配对就不能宣称第三方 provider 全兼容。保留真实账号测试的独立授权与结果边界。

## 2026-11-11 — 后台模型调用必须使用会话 provider registry

- **来源**：用户反馈主对话 CC 已可用，但 impression 蒸馏报 `No API provider registered for api: claude-code-stream-json`。
- **原则**：固定模型与跟随当前模型都走会话 registry，由其解析认证与 provider；不能把主对话可用当成旧 compat 全局 API 表也已注册。回归使用仅注册于会话的 provider，同时覆盖 tool_result 与 recall。历史 system 消息必须作为数据处理，不能让其工具声明重新进入无工具蒸馏请求。
- **边界**：插件混合 Vitest 与 node:test 时按 runner 分别执行，仅收集当前 src/eval，不混入历史归档。假 provider 证明调用路由，不冒充真实 CC 账号实测。

## 2026-11-11 — 代理连接与上游 HTTP 身份必须同时验证

- **来源**：用户要求 Pi 经真实 CC 可用，拒绝将 403 或隧道建立冒称成功；最终在 tmux 中 Pi 返回 ok。
- **原则**：CONNECT 成功不证明 HTTP 请求使用该 socket；自定义连接必须保留上游 Host，不能因删除入站 Host 且漏传 hostname 而发送 localhost。先用本地 HTTPS/CONNECT 回归断言路由、Host 和完整响应，再执行获授权的一次真实对话。未排除 HTTP 请求差异时，不把错误归因于 TLS 指纹。
- **边界**：测试超时、取消或未消费响应流均不是通过；报告须包含退出状态与取消数。日志不得输出代理凭据或认证头；一次真实成功只证明当前模型与环境通路，不外推全部模型和缓存效果。

## 2026-11-04 — 设计文档按 owner 分权，完整设计不等于审查或实现完成

- **来源**：用户要求按 QPDI/workflow 完成本插件全部设计，其他插件与外部服务的修改统一写入 docs/extern-dep-design.md。
- **原则**：内部文档只承接自己的 P/M/R 和叶子函数，外部接口/修改在一处规范化，历史候选归档并指向当前权威。Q.I只记用户意图；单池、容量声明、默认凭据文件等是待批准的D选择/前提，不反写成用户已确认。源码存在不等于caller可直接调用，但可组合的公开SDK路径要用隔离证据判断，不能过早断言只剩私有配置绕行。
- **边界**：文档齐全、机械链接通过、少量离线探针均不证明生产或审查通过；独立审查、真实网关、真实KEY和发布仍需对应授权。批量精确编辑只提交有效替换，不放无变化/占位项，避免一个未命中令整批修改失败并产生无必要重读。

## 2026-11-04 — 加载期服务协议要以真实提交顺序证明，而非靠等待想象

- **来源**：用户要求 new-providers 来源服务的代码级可行性细化；实际 Pi 1.4 loader 原型在两种 factory 顺序、覆盖、缺服务、构造失败及错误实例 ID 共七场景通过。
- **原则**：消费者先订阅就绪再同步查询；提供者先挂查询 handler，再在初始化最后发布就绪；实例工厂同步返回最终身份的标准 Provider，网络留给标准异步钩子。用真实 loader、全量 offline refresh 和 CLI resolver 证明首次模型可见性，不能用组件方法存在或 selected refresh 冒充启动路径。
- **边界**：事件发布早于提供者 factory commit，发布就绪后再失败没有跨扩展自动回滚保证；登记调用返回可能仅表示排队。原型未执行的配置、UI、网关和完整生产回归继续明确标为未测，不把七项机制证据扩张成整套产品已完成。

## 2026-11-04 — 静态声明可标识 Provider 构造服务，不必复制能力描述

- **来源**：用户进一步指出，配置只需登记约定服务名，由公开接口定义提供者如何被驱动，不必让 provider-profiles 静态维护整套属性。
- **原则**：静态配置决定查找哪个服务，服务按实例声明构造标准 Provider；原生来源与扩展服务统一为来源创建入口，后续注册、认证身份、模型归属沿用既有语义。来源定义按用户约定新覆盖旧并警告，但不擅自覆盖实例身份或凭据。认证、模型目录、刷新和请求复用已有 Provider 接口，不重定义同义 RPC 或额外 TYPE 注册表。
- **边界**：服务名不是可用性证明；读配置可以先发生，服务必须赶在实例构造及首次模型解析前就绪。顺序加载 factory 时不能阻塞等待尚未加载的提供者，可提前加载或用加载期就绪通知与同步创建完成登记。缺服务明确报不可用，不退成其他来源；用量查询保持独立公开。“统一流程”不等于保留旧克隆器的全部内部假设。

## 2026-11-04 — 先用足够的静态声明消除启动依赖，不先增加缓存代理

- **来源**：用户在 provider 可行性报告后指出 provider-profiles 已读取配置，可以预先声明关键静态性质，简化初始实例注册。
- **原则**：区分构造初始 Provider 所需的静态信息和运行时登录/管理行为。若配置可提供官方模型来源、连接地址、协议与兼容性质，就先构造标准实例，使模型在初始选择前可见；缓存不再被升格为启动正确性的必要条件。模型容量引用官方目录，不另维护硬编码副本。
- **边界**：静态声明不能替代函数行为、服务初始化、团队上下文、单实例保证或缺失的真实额度权重；新增配置项必须承担现有字段无法表达的实际职责，不借简化名义扩成通用脚本平台。

## 2026-11-04 — 可行性必须核到调用者可见接口与启动时序

- **来源**：用户要求按 workflow 调查有源码依据的完整可行方案；实际安装版探针发现 ModelRuntime 有 login，但扩展的 ModelRegistry facade 没有；session_start 又晚于 CLI 模型解析。
- **原则**：分别证明接口存在、当前调用者可调用、调用时机满足目标。以实际安装版本为运行依据，不能用工作区目录或另一层的公开方法补缺。研究原型只证明它实际执行的机制；例如缓存先行恢复可以跑通，但不等于完整 CLI、真实网关、并发启动均已通过。
- **边界**：源码上可添加的能力必须标为待实现，不把创建 token 成功当成已拿到 key，不把无限 token 当成用户虚拟余额无限，也不把逐 key 百分比当作异档池总容量。子任务超时保留其材料与失败，不冒称其执行成功或重跑洗掉成本。

## 2026-11-04 — 先复用运行时 provider 表，不因静态消费者限制另建 TYPE 服务

- **来源**：用户指出让 /add-login 读取运行时动态 provider 表就是通用改进，无需为 throttle 另设 TYPE 发现与注册服务。
- **原则**：先检查官方运行时注册能力，把消费者的静态来源限制改为通用来源解析；命令补全、配置校验、创建和重启恢复共用该解析。不把当前消费者只支持内置来源误判成平台不能注册新 provider，也不在官方注册表之外重复维护 TYPE 名单。
- **边界**：可发现不等于可安全克隆；认证、动态目录和刷新状态仍须按实例身份正确绑定。运行时来源不能复用跨会话静态缓存，只有真实缺失且当前任务必需的能力才另增公开接口。

## 2026-11-04 — provider TYPE、实例 ID 与池成员不可互换

- **来源**：用户纠正 `/add-login my-zai throttle-zai` 中 throttle-zai 是 provider TYPE，最终模型必须属于 my-zai，而不是把 my-zai 当作池成员名。
- **原则**：NAME 确定 provider 实例身份，TYPE 提供创建和登录行为，模型归属及凭据按实例绑定。优先复用运行时 provider 注册表及标准 Provider 的认证与模型接口，命令创建、配置校验和启动恢复采用同一类型解析；用量按实例实际连接的池查询。
- **边界**：实例名不自动等于池 ID 或池成员名，TYPE 也不决定多个实例是否共享同一池。不能只修正显示名称而保留错误的注册、持久化和用量查询身份。

## 2026-11-04 — 网关接入按公开能力解耦，不以标准接口补造缺失数据

- **来源**：用户要求 throttle provider 的账号导入、服务启动、模型目录与池用量各归其主，只通过公开接口协作，上游 PR 不得带入 Pi 插件需求。
- **原则**：先区分 provider TYPE、实例 ID 与池成员身份，以及上游 key 与网关调用令牌；复用既有查询的简略与详细结果，不另造两套查询。外部用量服务未认领才回退内置，已认领后的失败必须保留。上游只补独立成立的服务能力，不接受客户端专属字段。
- **边界**：模型 ID 列表不提供上下文长度，逐 key 百分比也不提供绝对池容量；缺少元数据或容量权重时必须明示，不能凭兼容协议、接口扩展或百分比相加声称完整自动发现与总池额度。

## 顶部widget点击不能替代结果消息卡点击

- **来源**：用户再次指出Loop ·结果卡仍不能点开；之前实际只接了顶部widget，误把相近交互对象当作同一项交付。
- **原则**：验收绑定具体组件与动作，不能以邻近组件可点击或全局Expand可用代替消息卡单击。标题局部交互与正文选取分开；每条消息状态独立，保留宿主全局Expand，实例间不共享可变状态。
- **边界**：只补明确授权的交互，不改官方宿主；直接在真实全屏TUI点击目标卡，并单独确认legacy原行为，不把调用选项或mock自述当实测。

## NoWake的安全追加边界不等于整段AI回复结束

- **来源**：用户要求用60秒在途窗口区分follow-up/steering；实际6条唤醒消息在原回复final后消费，但两条NoWake在工具轮结束后、final前追加。
- **原则**：按实际消息顺序判断本轮投递；技术turn_end、整个agent run与用户看到的完整回复不是同一边界。NoWake不启动新run，但可被仍在运行的AI看到，不能承诺只在下一次人工对话才可见。
- **边界**：存档时间不是脚本结束时间；稍晚触发但同批消费的消息不证明空闲启动。留原始标记与顺序，不追加宿主改造或泛化成所有情形的正确性证明。

## 2026-10-20 — 性能归因先分解墙钟与执行，身份槽只用于有消费者的调用

- **来源**：用户质疑 FSM mock 主体232秒；此前误称 child 冷启动约20秒、正常结构成本。原始session显示读文件仅2ms却在调用前等10秒；隔离真实daemon证明普通权限检查前多余identity acquire留下未消费槽，同名重入按10秒TTL阻塞。不带该写槽的同类检查仅114–129ms，child首次回复仅1.12秒。
- **原则**：先区分模型/prepare hook/工具execute/并发等待及endpoint后空转；总墙钟不能从工具durationMs或请求总数直接推因果。对照用相同二进制、请求、身份与隔离状态，一次只变相关步骤。先核槽的生产者和消费者，再加身份握手；同文件的TTL与查询timeout不能混读。残余38.3秒无分段计时就保留未知，不补写冷缓存故事。
- **边界**：定位和实验不等于生产修复；不同版本的OC历史耗时不是严格A/B基线，不因缺陷推导新增常驻池、预编译或改短服务端TTL。

## 全球插件默认短英文，投递参数不能冒充实际排队路径

- **来源**：用户要求Loop实际文案用短英文，并追问NoWake是否也进入follow-up；原答复把所有调用传followUp说成所有结果都排队，不准确。
- **原则**：产品默认运行文案不随当前中文对话改成中文，用户prompt/路径/输出保持原文。分别判断调用选项、宿主条件分支与UI可见性：NoWake只追加会话，忙时延后到turn end；唤醒结果忙时进agent.followUp，而官方可视队列不一定包含custom消息。
- **边界**：不为展示修改官方Pi，不把不可见判为未投递。测试输入的补全确认/实际提交，以及legacy历史文字/当前编辑区分开；失败原证保留，不因修正测试而宣称原轮全绿。

## Loop常驻摘要以预约项为单位，空态和可展开空间分别判断

- **来源**：用户把运行中widget改为等待/执行常驻摘要，并明确零项隐藏、legacy不展开、全屏最多10行以及show off/on只影响显示。
- **原则**：预约与执行按稳定item ID合并，一次任务执行中不能随调度完成而消失，重复任务不能双计。零项隐藏不是始终画0条；隐藏不是取消。展开测实际编辑区和其它widget占位，不用终端高度减固定猜数；倒计时只重绘缓存，不能每秒重新读任务存储。
- **边界**：只使用官方公开UI，未知布局保持折叠；当前直接测试及隔离Pi实测不扩大为新CCA/绝对零抛证明，不为展示功能增设调度或存储系统。

## 现场实测成功也要保留可追溯日志

- **来源**：用户要求实际测试成功也log；原七例摘要只有报告及/tmp路径，现保存8份实际custom消息与统计到既有测试文档目录。
- **原则**：成功、预期失败、超时都保留实际输入关联/正文/退出状态/判定和时间；预期脚本失败不等于用例失败，消息持久化也不等于单独启动AI回合。通过结论有范围，不只记口头“都过了”或只依赖临时文件。
- **边界**：只记录本批授权数据，不把日志请求扩大为生产新日志库、重新运行测试或补做点击功能。

## 等待定时回执的实测必须抑制Boulder提前续跑

- **来源**：现场安排两分钟后sleep10秒再唤醒时漏设inhibitBoulder，先收到的是Boulder待办提醒；用户明确指出遗漏。
- **原则**：这类等待由定时结果承接的实测创建时带inhibitBoulder:true，不能把Boulder提醒误认成脚本结果。补救前检查原任务是否已发起，保留原deadline；已发起则不重建造成重复。一次性progress completed只表示发起过，不冒称脚本结果已收到。
- **边界**：用户对漏flag的纠正不授权改生产代码、回退或新增另一个唤醒；按真实回执收尾。

- **原则**：同屏控件复用宿主当前主题的底色和前景色，标签用内边距而非方括号；按钮距右边 3 列，由 editor 同色边框横线续接。视觉按钮与鼠标命中区一致，右侧边框不得触发清理；主题变化和 resize 后按当次渲染更新。
- **边界**：样式修改不改变清理、剪贴板、双击退出及异常隔离语义；主题样式调用失败也不得产生不可见的有效清理区域。

## 可选输入框按钮不能把钩子故障变成宿主异常

- **来源**：用户批准 fullscreen Clear 按钮试做后，明确要求不要产生 exception；按钮位置指定为 Working 同行最右侧。
- **原则**：可选运行时钩子先检测，安装中途失败撤销自己的改动；绘制、鼠标动作和卸载边界不外抛，失败不伪报成功。鼠标动作绑定被点击的 editor，而非瞬时焦点；release 仅恢复自己仍持有的方法。
- **边界**：故障注入和原生 renderer 测试只证明所测边界，不证明宿主、终端或第三方插件永不异常；新增按钮的防护不授权改动默认 Ctrl+C 的复制行为。

## 闭源部署件的缺件处置与幂等注册的预检

- **来源**：用户修正 /cca-reasoning skill：缺件不应一概“报告未部署并停止”；部件不开源时，语义不明的缺件=本机不适用，直接不执行；已注册的定义应先查存在再无视注册步。
- **原则**：对外发布的操作型 skill 要区分“可排查故障”与“本机不适用”：前者给排查命令，后者直接退出且不安装、不解释。幂等操作（如注册）也应先做存在性检查，已存在则跳过，降低无谓副作用与噪声。
- **适用**：跨机发布的技术 skill、闭源工具链探测与幂等命令编排。

## Clear-only 必须是防误触默认路径之外的显式动作

- **来源**：用户纠正快捷键方案：Ctrl+C 复制后清理是为了防止误触丢失长输入，不能把复制保护迁到复杂键。
- **原则**：保留 Ctrl+C 的复制后清理；新增 Ctrl+Option/Alt+C 才绕过复制直接调用原清理动作。新增能力不得反向削弱用户已有的默认保护。
- **边界**：源码无绑定冲突不等于终端或系统不截获快捷键；用户批准快捷键实现后，鼠标 Clear 按钮仍只调研，不能顺手扩大为接入。

## Impression 的系统化测试按状态和判定覆盖，不按请求数量定义

- **来源**：用户连续要求自行制定多维测试依据，并纠正为明确、系统化、能覆盖各种抽象状态的执行方案；此前又允许改用zai-001-g-l，但明确要求上下文短以免耗尽额度。
- **原则**：分别定义任务用途、信息状态和抽象视角；每格都要有最小差异用例、独立产物断言与能被拒绝的错误反例。不能以全模型交叉和重复次数代替内容覆盖，也不能以关键词齐全证明逻辑关系正确。语义值、必要格式、首次信息充分与补读后成功分别计量。开放文本尚不可判的部分保留待判，不自动加模型评委或审查循环。
- **执行边界**：先固定模型测状态，再分层扩展模型角色与组合并明确各层未覆盖部分；新用例不自动继承旧矩阵的调用额度。换账号后用短fresh任务卡，不继承旧实现会话或传递全套历史报告。测试方案落盘不等于用例已实现、模型已通过或已获生产采用授权。

## Impression 单元硬截止须包含进程终止宽限

- **来源**：用户追问真实测试进度；实现代理已交付但父协调者尚未启动真实批次。准备启动时发现单元600秒取消后另加60秒强杀等待和5秒宽限，且 `child.killed` 会在发送SIGTERM后阻止SIGKILL。
- **原则**：本实验的10分钟约束覆盖实际执行到最终终止，不能在其后追加宽限；已发信号不等于进程退出。直接测试须含忽略SIGTERM的子进程，并确认队列收尾与兄弟隔离。实现代理完成、离线测试通过和真实矩阵已经启动必须分别报告；交接停顿属于协调者责任，不再伪称等待用户授权。
- **边界**：仅修复已授权的单元截止要求，不因此追加审查轮次或扩大实验范围；真实批次未启动时明确报告零进展，不用实现完成数替代实验完成数。

## Impression 接线测试不能只覆盖不可用模型的提前返回

- **来源**：真实首轮4个接线单元在 `RunRecorder.attach` 与 `executeUnit.finish()` 之间统一报错：前者禁止子进程写总记录，后者却无条件append。此前CLI离线smoke只走model-unavailable早退，89项测试未覆盖这条完整组合路径。
- **原则**：子进程单元执行、独立结果文件和父进程合并必须用正常结束及执行失败路径直接连接测试；早退成功只证明该早退。结果保存错误不可遮蔽原执行错误。真实接线失败应保留原始尝试、源码与工件，停止扩散到全矩阵，不能算模型质量失败或删除后伪称首次成功。
- **适用**：impression-demo 的多进程runner、record sink接线、离线smoke和真实批次恢复。
- **计划身份补充**：准备真实矩阵时发现计划ID含mode而执行ID不含，且父停止门拿两种格式的ID作匹配。计划/记录的逻辑身份须一致，文件安全化是另一层；模式改变必须得到独立工作区。停止门还依赖原始故障正确分类及接线组真正先于后续调度完成。定向测试应连接这几个边界，不能以单独的计划计数、记录测试和队列测试均通过代替组合路径成立。
- **无交付的执行边界**：tmp-low修复轮在约9分半内仅完成读取，挂起的是源码读取命令而非测试；终态因缺结构化报告被拒，源码差异为零。必须分别报告工具等待、读取、实施、测试和交接，报告格式修正也不能冒充实现完成。没有shell子进程不证明具体阻塞根因；不为已经明确的局部修复反复重开探索，也不在治理子代理失败后未经用户许可切换本地实现。

## Impression 实验约束必须落在实际执行路径，而非配置与报告字段

- **来源**：本轮 glm-5.3 实现的 demo 虽有 41 项离线测试通过，6.1-sol 仍发现八项合同缺口；父协调者核读相关代码后批准修复，修复后直接运行 70 项测试、类型、lint 与根检查通过，未运行真实模型实验。
- **原则**：cwd 不构成文件或凭据隔离；必须在工具层限制访问。配置模型标签不证明实际调用模型，记录身份要来自请求与响应。调用/时长上限必须在每次真实请求及会话中执行，不能只预估或记录；无法执行的金额上限应明确拒绝。原文回退后任务正确与实验调用无故障是不同结果，失败不能从计划分母消失。可重复实验还依赖完整上下文、无损逐次产物和全新工作区，不能靠摘要预览或旧答案判成功。
- **边界**：faux/直接功能测试证明的是所测链路和反例，不证明真实 provider 可用、效果提升或普遍不劣于原文；修复自述与直接测试不冒充第二轮独立审核。长实现须保留可恢复产物和阶段状态，超时不等于没有改动。
- **适用**：impression-demo 的对照实验、真实模型矩阵、隔离执行与结果声明。
- **启动故障边界**：tmp-Haokun子代理首个请求被400/1214“角色信息不正确”拒绝且源码差异为零；只能说明该请求被拒，不能凭错误文案猜具体字段或否定provider在其它上下文的可用性。随后缺少file-only产物是连带结果，不是独立的文件写入故障。连续基础设施失败后，保留部分工作并请求明确的本地收尾授权，不盲目换账号重试。
- **OC对照补充**：用户要求对照OC后，脱敏配置与离线构造确认相同端点/model下，Pi的reasoning模型默认发developer，OC的openai-compatible适配器发system。自定义网关不会因真实模型是GLM而自动获得Z.ai兼容设置；优先用显式supportsDeveloperRole覆盖来对齐角色，不把关闭推理当修复。离线请求构造证明协议差异，不证明服务端唯一根因或修复已通过；凭据未完成同一性比较时也不能断言账号完全相同。角色修正后出现1210，服务端仅列low/high/max；离线ModelRuntime却确认旧参数是medium而非none，因此不能把服务端“关闭思考”文案当作客户端实际关闭的证据。按明确支持档位用low新合同接续，不盲目关闭reasoning或批量改其它兼容项。
- **真实接线补充**：首轮落盘错误还遮蔽了Codex传输失败；GLM响应的请求标签为 `glm-4.7`，服务端 `responseModel` 却为 `glm-5.3-flash`。发现一个宿主错误不证明不存在其他错误，SDK模型字段也不能取代服务端返回身份。后续实现代理因429/1310周额度失败而停止；保存部分源码和测试证据，不静默换账号、换执行通道或开超额。生成、评分、持久化和完整交付须分别陈述，已发请求不能因没有终态记录就说未调用。

## 异常传播与无异常外逸是不同合同，空分析集不算语言支持

- **来源**：用户补充插件忌讳抛异常并询问逐函数 Hoare 推理；现有测试明确允许 client/loop throw。指定 Analysis 工具对真实 TS 模块返回 exit 0 但零函数，已有语言控制样例可抽取 38 函数。

## Impression 先保任务信息效用，再选择压缩与引用形式

- **来源**：用户纠正 Impression 提示词方案：核心追求是高效填充信息，使下游行为接近乃至不劣于直接读原文，删去垃圾信息；大段引用和减少 passthrough 只是可能的手段。
- **原则**：先将当前任务的信息支撑与下游完成质量作为设计目标，再讨论摘要、原文选摘和透传；不能把短、引用多或透传少当成质量证明。保留必要条件、例外、反证与范围，不把符合预期结论当作相关性。现有字符长度回退只是实现策略，不因已存在就成为目标；当前机制不能证明普遍不退化时，应报告设计保证缺口，不能反写为用户接受质量损失。按实际加载链路定位提示词，包括代码内嵌文字，不为一致性机械修改未启用的历史模板。
- **适用**：Impression 提示词重构、信息选择、引用展开及原文对照的下游效果实验。
- **实验边界**：用户进一步明确，大幅提示逻辑变更在不同模型上的效果和效率未知，绝不能直接生产使用。先用隔离的 impression-demo 与冻结原文／生产基线比较；蒸馏模型和下游执行模型是独立变量，笔记评分不能替代任务完成质量。模型调用、数据发送与预算须事先获准，实验通过不自动授权生产晋升。

## 跨插件信号写者不应承担消费者的运行副作用

- **适用**：Boulder 抑制协议、跨插件日志与持久信号的生产/消费边界。

## Loop defer 先确认时间语义，再改变执行进度

- **来源**：用户要求先给方案、不要修改内容，随后批准仅延期下一次触发、不修改周期定义的方案；自行测试教程又明确要求“长话短说，直接命令群”，实际测试通过后授权提交并推送。
- **原则**：调查实现方式不等于获准修改；先明确相对时间的基准以及“临时”是否要求恢复原钟点。当前 Loop 周期按实际执行时间推进，延期只写当前 session 的 `nextRunAt`，不改共享定义或新增暂停状态；在用户批准方案后才实现。用户只需自行操作时，给最短可运行命令群、ID 替换说明和一个预期结果，不展开多组可选测试。功能交付时同步当前有效的功能清单与 Q/P/D/I，不能只改 README 和详细设计就声称全量同步；用户排除 audit 后，不追加审查或改写历史审查材料。时间点/周期的存储区分不等于重启补执行/丢弃策略已有区分，后者必须直接沿恢复和到期路径说明。用户进一步确认：周期关闭时剩三分钟，重开仍剩三分钟；过去的一次性截止点过期而不补执行。剩余倒计时需要实际关闭时刻，不能用创建或上次执行时间冒充；只有正常 shutdown 保存成功才能承诺精确恢复，强杀/崩溃的缺口必须说明。
- **适用**：Loop 用户命令、共享定义与私有进度分层、分阶段设计授权。

## AI 留言方案先区分固定展示与按需历史

## 剪贴板请求与系统采纳是不同责任边界

- **来源**：clear-to-clipboard 设计中，用户明确要求长粘贴复制为 `[paste#ID <actual text>]`，插件只需向系统发起复制请求，不负责系统是否写入；此前方案擅自加入等待、失败阻止清空和双击时序变化。
- **原则**：先按用户定义区分“发起请求”与“外部确认”，不能把后者偷渡为功能前置条件。需要保留宿主原按键行为时，在实际 action handler 内同步取得请求文本并触发异步 API，再立即交还原 handler；不要等待 Promise 再重放可能作用于新实例的清空。格式同时依赖标记 ID 与正文时，分别核对它们的真实持有者和公开 API，不能把只有标记的 `getText()` 或只有正文的 `getExpandedText()` 冒充完整载荷；若只能依赖私有运行时字段，标明版本边界并做直接功能测试。
- **适用**：Pi 扩展的输入拦截、长粘贴格式化及任何外部副作用的责任界定。

## auth.json 可带团队元数据，但不能只加一个任意字段

- **来源**：用户要求确认独立团队 key/组织/项目能否放 auth.json。Pi 的 `ApiKeyCredential` 已支持 `env`，`ModelRegistry.getApiKeyAndHeaders()` 返回 resolved env，具名 provider 的 `wrapApiKeyAuth` 仅在自有 stored credential 有 `key` 时转发 env；两具名账号目前没有 auth.json 凭据，仅靠 profile 配置的推理 key。
- **原则**：物理可存、符合既有结构、插件能通过公开接口取得，以及不改变推理凭据是四项独立条件。可将 team key/IDs 放当前 provider 凭据的 `env`，但必须同时为别名保存正确的推理 key，且这会覆盖原 profile key 的优先级并可能随登录被改写；未知新字段不会被原生解析。若不接受复制与覆盖，独立 0600 插件凭据文件更稳妥。不要把团队 key 替换 `auth.json` 的 `key`。
- **适用**：provider-usage 与 provider-profiles 共存时的团队凭据配置设计。

## 真正团队额度凭据需要与模型推理凭据分开存

- **来源**：用户提供含实际 team key 的本地 Python 脚本。脱敏读取并按脚本同域请求实测：该 key 与两个具名模型 provider 的 API key 均不同；无参数 quota 业务 500、`?type=2` 不带组织/项目返回 `data={}`，带其组织/项目头后 `success:true` 且有 2 条 CREDIT_LIMIT。
- **原则**：证明三元组 key+organization+project 可用后，停止猜 web token 或并发多个失败接口。用量凭据若不同于模型凭据，应放插件拥有的独立 0600 本地配置中、按当前运行时 provider ID 显式关联；不把 team key 塞进用于模型请求的 auth.json provider 项，更不直接复制用户脚本中的明文密钥到仓库。关联前先确定哪个模型账号确实消耗该团队额度，否则 footer 会显示别人的余额。
- **适用**：provider-usage 团队凭据存储与当前 provider 额度归属。

## 看“官方插件”须追到脚本而不止官方文档

- **来源**：用户要求检查智谱官方 `glm-plan-usage`。官方仓库 `zai-org/zai-coding-plugins` 的 `query-usage.mjs` 实际读取 Claude Code 的 `ANTHROPIC_AUTH_TOKEN`／`ANTHROPIC_BASE_URL`，用原值 Authorization 顺序查询模型/工具用量与不带 type 的 quota 接口；没有团队 type=2、组织/项目头或成功非空额度验证，HTTP 200 的空数据也会打印。
- **原则**：文档称“仅个人版”要用实现路径验证其因果范围；别把同名社区包当官方源码。实际脚本只证明个人通路与原值认证示例，不证明团队 API key / browser token 任一可用；模型/工具用量查询还不同于剩余额度。
- **适用**：provider-usage 参照官方插件与团队额度决策。

## 社区团队额度请求示例不等于成功响应证据

- **来源**：用户提供 Gemini 汇总声称团队 `?type=2` 必须 `Authorization: Bearer <团队API_Key>`、组织/项目 ID 在 URL、官方插件可用。核对引用后，官方 `glm-plan-usage` 明写仅支持个人；引述的 sub2api issue 是请求示例而非成功响应，认证示例反为 raw key 且 Bearer 两者可能被接受；既有两账号 raw/Bearer 实测均返回空 `data={}`。
- **原则**：对汇总答案逐条回到所引原始页面：把团队产品存在、请求示例、可获得上下文的位置、真实带额度成功响应分开；只有最后一项证明能够接入。不要因 HTTP/业务成功或二手答案给出 `Bearer` 的定论，先配齐组织/项目再观察有效数据。
- **适用**：provider-usage 团队查询接口认证、外部来源与验收门槛。

## 团队额度的 key、网页 token 与租户标识不可混称

- **来源**：用户要求单独提交 provider-usage 后再讨论 team token。已查两具名账号的 key 来自 profile 配置，`auth.json` 没有它们的 credential；Pi 现有 ApiKeyCredential.env 可携带 provider 元数据，`getApiKeyAndHeaders()` 可暴露 env，但别名缺本地凭据时不能靠往 auth.json 随便加新字段获得该值。外部实现对团队额度究竟接受 API key 或网页登录 token 存在分歧。
- **原则**：先验证“现有 API key + 当前组织/项目”是否得到非空额度；若成立，仅需显式账号上下文配置，不需新 token 或更改模型 provider。若必须用网页 token，再独立讨论其安全存储、刷新和认证边界。共享工作区仅提交本职插件目录，保留其他已暂存/未暂存改动，不把无关本地学习记录混入提交。
- **适用**：provider-usage 的团队额度设计与共享工作区提交。

## footer 冗余字段与 thinking 显示要分开处理

- **来源**：用户决定团队额度容后再议、删去 footer 中与右侧重复的 NAME，并报告模型跑完 thinking 显示 off。插件发现仅监听 thinking_level_select，而宿主只在档位实际变化时触发它；footer 未初始化时把 undefined 显示为 off。
- **原则**：仅从自动 footer 删除 provider 前缀，多账号详细命令仍保留名称；不改团队认证/账号配置。右侧思考档位应在会话开始读取宿主当前 thinkingLevel，并在模型切换/turn_end 同步，而不能从“没有选择事件”推断实际 off；区分 UI 丢状态与模型推理档位被更改。
- **适用**：provider-usage footer、Pi extension 事件与显示状态。

## 具名 provider 的团队头配置必须核对注册器冲突规则

- **来源**：用户追问两把团队 key 是否可配置组织/项目。查实 provider-profiles 的配置解析忽略 entry 中的未知 `headers`，且同名 `models.json.providers[id].headers` 和 `modelOverrides[modelId].headers` 都被判冲突；模型元数据的无头 modelOverrides 才可共存。当前用量插件又按国际模型 endpoint 路由并拒绝国际路由带团队头。
- **原则**：不能笼统建议“给具名 provider 配 headers”，也不能误以为改用 modelOverrides.headers 就避开冲突。先核对实例注册器的冲突规则与实际模型 endpoint；明确分开“未来可扩展显式账号额度参数”“现有额度路由会用这些头”“仅用 API key 就能自动发现组织/项目”三项。为只读验证可直接向团队额度请求提供同账号组织/项目，无须预先修改模型请求路由。
- **适用**：provider-usage、provider-profiles 共存的配置建议和团队额度诊断。

## 并发候选只以有效额度为胜出条件

- **来源**：用户要求先实验团队账号的多个参数、认证形式和接口，再考虑并发查询与修改路由。两个账号在三个 host 的 `?type=2`、raw/Bearer 认证均得 `success:true` 却只有 `data={}`；无 type 失败，另一统计接口非 JSON。
- **原则**：实验要限定在有接口证据的候选，记录每种候选的状态与有效额度字段，而不将 HTTP 200、业务成功、空对象冒充查到额度。不能因为三处主机都返回相同空对象就认定国际/国内来源或做 `Promise.any`；有至少一个账号的明确有效额度实测前不建立多路并发胜出机制。缺团队组织/项目时明确这一验证边界，不擅改模型 provider。
- **适用**：provider-usage 的 Z.AI 团队探测、响应解析与候选并发策略。

## 团队额度先作完整的只读探测，不能先改 provider

- **来源**：用户要求先确定两个团队账号是否能查到额度、查到再改。两个 key 对国内 `?type=2` 均返回 HTTP 200、业务成功，但 `data={}`，没有可显示的额度；当前本地配置缺组织/项目上下文。
- **原则**：HTTP/业务成功不等于读到有效额度，要检查响应中的实际额度字段。团队查询应先取得各账号组织/项目上下文，发送完整只读请求并看到非空有效额度，再决定是否改模型 provider；不能以先切模型路由替代额度可用性验证。
- **适用**：Z.AI 团队套餐实测与后续配置变更。

## 团队账号的缺参请求不能证明 key 无套餐

- **来源**：用户确认 `zai-000-g-l`、`zai-001-g-l` 是已刷新额度的团队套餐 API 账号；此前只测试无上下文和 `?type=1`，便把业务失败/空订阅列表解释为无法查询或无付费套餐。
- **原则**：团队额度的有效请求前提是 `?type=2` 与同账号 `bigmodel-organization`、`bigmodel-project`；没有这三项时，HTTP 200/业务 500 与空个人订阅列表只说明该不完整请求失败，不能用于否定团队额度。不得据此将这两个账号隐藏为不适用；也不能仅按实例名改查询地区。取得当前账号的组织/项目上下文后才可以验证团队额度成功与否。
- **适用**：provider-usage 中 Z.AI 团队账户的状态分类、地区路由与下一次实测。

## 刷新闪烁的修复止于状态写入点，不扩成新的失败策略

- **来源**：用户要求同账号刷新时保留旧额度，不在启动请求时重置为省略号，并纠正过度改造；随后明确失败时旧额度加 `(err)`，首次失败仍显示 ERR。
- **原则**：先定位实际将 ready 改为 loading 的所有写入点；只在同账号已有结果时不写 loading，换账号必须清旧值。失败是否保留旧值是独立语义，不可自作主张改；获明确要求后用当前 DisplayState 的旧成功值加错误标记，未有旧值仍走既有错误结果，不引入历史库或重试策略。
- **适用**：provider-usage 的 footer 刷新与错误状态。

## 两地区额度失败不证明 key 的地区归属

- **来源**：用户怀疑 `zai-000-g-l`、`zai-001-g-l` 实为国内 key；配置却把两者注册为 `zai`。逐一用各自 key 查询 CN 原额度、`?type=1` 与订阅列表，仍为业务失败/空列表；其中一个 key 还与本地两个内置槽位完全相同。
- **原则**：先将 provider 注册的服务端点与额度请求地区分开。对一个地区的额度业务失败可能是套餐或组织上下文缺失，不能反推 key 属于另一地区，也不能靠把用量插件按实例名称强制路由到 CN 伪装修复。若确需改变 provider 来源，应由用户确认其模型请求也应切换地区，随后按当前 provider 的真实端点自然路由，并单独处理套餐上下文。
- **适用**：本插件的区域路由、具名账号排查与 provider 配置变更。

## Z.AI 的业务 false 必须按套餐服务面与上下文解释

- **来源**：用户质疑两地区 `success:false` 是否等于额度 100%；实测内置与具名 API key 的额度接口无 limits、业务 code=500，订阅列表返回成功空数组；公开团队案例显示缺 `type=2` 与组织/项目头可得到相似失败。
- **原则**：`success:false` 是业务拒绝而非已用比例。国际 API-key 服务面只在精确失败与同账号空订阅列表同时成立时判不适用；国内同文案若缺团队上下文不能判无套餐。团队组织头必须从当前模型原生认证成对取得，绝不从 provider 名称、profiles 或别的账号推断。无当前 key 的成功额度响应时只声称协议路径实现，不声称真实套餐已通过。
- **适用**：provider-usage 的 Z.AI 国际/国内用量接入与范围声明。

## 测试桩支持不是目标账号套餐可用

- **来源**：用户追问为什么 Z.AI 国际和国内没有实际用量；实际 TUI 两者均显示 ERR。只读请求确认国际和国内存储 key 对额度端点均收到 HTTP 200、业务 `code=500`/`success=false`，而此前只用样例测试过成功 JSON。
- **原则**：对某 provider 的“支持”应区分已注册路由、成功响应解析、当前账号可用三个层次。HTTP 200 但业务失败不能展示 mock 额度，也不能仅凭通用“无 Coding Plan”文字断言非套餐，因为国内缺参数/组织上下文可呈现相似失败。无源证的失败状态只报 ERR 和剩余缺口，不把它升级为不存在套餐。
- **适用**：provider-usage 的 Z.AI 两地区真实接入、状态展示及能力声明。

## Footer 只承载快读量，长内容交给按需命令

- **来源**：用户否定底部 `(codex-002: 已用 72%(week) 重置…部分信息未解析)` 过长，指定用 `(codex-002: 72%(week))` 取代 `(sub)`，并要求按需查询及类似 impression 的多参数 Tab 补全。
- **原则**：从同一份已验证用量结构分别生成 compact 和 detail，不从详细字符串截取；footer 仅保留名称、已用比例与真实窗口，详情命令承担重置/其它额度/解析提示。命令的多目标列表只能来自运行时模型 registry，不能建立 profiles 依赖；Pi 的强制 Tab 需补全 provider wrapper，普通 getArgumentCompletions 不足。
- **适用**：provider-usage 的输出契约、命令与 TUI。

## 额度插件的假凭据测试必须与原生 OAuth claim 同形

- **来源**：provider-usage 的 mock JWT 把 `https://api.openai.com/auth.chatgpt_account_id` 伪造成扁平键，测试全绿但真实 Codex 登录解析需要 `https://api.openai.com/auth` 对象内的 `chatgpt_account_id`；按官方 OAuth 源码修正并实测。Pi 无可用模型时另用 `provider=id=api="unknown"` 占位符，曾被误显示为 `(unknown: ERR)`。
- **原则**：跨模块身份接口的测试值必须复制宿主真实嵌套数据形状，不能让 mock 自己发明契约；纯插件的 TUI 需在无模型的真实启动环境验证占位符处理。类型检查和自制 mock 的全绿不替代一次真实宿主接线测试。
- **适用**：本插件的 Codex 认证、模型选择和 TUI 加载。

## Q 只承担用户的正确性定义，设计和交付过程不冒充 Q

- **来源**：用户要求 provider-usage 原则文档按 QPDI 保留真实意图；随后又明确确认 Impression 中已授 `skip_impression` 余额不因配置上限下降而追回，并要求以非追溯原则记入 Q。
- **原则**：Q.I 用用户明确的正确结果、边界及反例定义并给出处，不把现有代码恰好如此倒推成授权，也不把一项功能的非追溯选择升级为全部配置的全局法则。已授额度保留属于用户确认的 Q.I；领取时如何限幅、当前余额与新上限的关系属于对应 P/D，应同步改掉与该 Q 冲突的“永远不超过当前上限”不变量。执行安排与 provider API 细节不冒充 Q。
- **适用**：provider-usage 与 Impression 的原则文档、配置状态设计及后续设计追踪。

## 用量监控必须保持纯插件边界

- **来源**：用户明确否定 provider-usage 设计里的宿主 footer 插槽与改源码授权要求。
- **原则**：本功能只能在插件内通过既有扩展 API 完成；指定原生统计行中的位置不授权新增宿主接口。应沿 setFooter 的插件绘制能力设计，不能因复刻统计有成本就擅自改宿主，或把自行制造的权限问题交给用户裁决。
- **适用**：provider-usage 的全部设计与实现。
- **边界教训**：`setFooter` 可控制原位排版，但它完整替换原生组件；真实 `autoCompactionEnabled` 不在扩展 API 中。必须明说 `(auto)` 无法可靠保留，不能把“纯插件能改同一行”升级成“原生行全部字段等价”。

## 设计文档只保留决定实现的内容

- **来源**：provider-usage 设计中，用户要求按奥卡姆剃刀缩短文档，同时不能遗漏必要信息。
- **原则**：Q/P/契约、分支、依据和真实缺口各写一处；删除重复的状态声明、流程解释与自述。简短不能省掉错误路径、边界条件或未完成项，措辞坚定不能把待证事项写成事实。
- **适用**：本插件及 Pi 扩展的设计文档。

## 解释集合算法时先说输入单位和参与范围

- **来源**：用户追问“按行切、怎么合并、谁参加”后指出，直接说“按 `/` 建树”没有说明 formatter 接收路径数组而非文本块，也没有明确已有 brace 表达式不参加合并。
- **原则**：解释合并算法必须先绑定输入单位，再说明分组范围、参加条件、排除条件和最终门。若输入是数组，不能含混地说“按行”；若某种已有表示不会被解析，必须用最小反例说明它与新原始项不会再合并。
- **适用**：路径压缩、批处理、集合归并、parser/formatter 边界和任何“哪些对象一起处理”的算法说明。

## 历史 compaction 文件路径不能用于判断当前文件是否存在

- **来源**：检查 live compact 时，错误地以摘要仍包含已删除模块路径为依据，判断它不是新版结果。
- **原则**：`read-files` / `modified-files` 记录的是形成该摘要时的历史工具调用；后续删除、重命名或改写文件不会回溯更新旧摘要。当前流程又会把上一轮摘要原样交给模型，因此历史路径可继续出现在 `S`。判断是否发生新 compaction 应看 session 中新的 compaction event、时间和对应运行版本，不能拿清单与当前文件系统做存在性比对。
- **适用**：滚动摘要、审计日志、事件溯源数据和任何历史派生清单。

## 新清单格式化不应扩张成历史清单维护

## 2026-09-17 — 最小接入点靠完整调用内封装，不靠压行

- **适用**：monorepo、源码别名、模块加载器、包发布验收与测试环境隔离。

## 2026-09-17 — 回退路径必须保留可区分的失败原因

- **来源**：用户实测 compact 得到 `unusable summary; using built-in` 后要求立即回退。新封装把空草稿、空展开结果、展开后超限都返回空字符串；现有记录又没有失败响应，无法确定实际触发项。
- **原则**：保持原调用接口简短，不能以丢失拒绝原因和关键指标为代价。多个有不同修复方向的分支共用回退行为时，至少保留原因与必要的非敏感长度/预算/停止原因；不要默认某个 transcript 插件存在或已记录返回值。证明拒绝分支会执行，不等于证明其条件适合真实使用场景，也不能用于认定某次失败根因。
- **适用**：compact、引用展开、输入/输出限制、降级链和模型调用诊断。

## 2026-09-17 — 索引接入不应附带新的接受/拒绝策略

- **来源**：用户否定 compact 引用封装中的额外输入估算和展开后预算检查，明确要求“原来咋整就咋整”。本次删除这些门槛，保留原有模型生成 `maxTokens` 和空正文处理，并保持入口停用。
- **原则**：引用标注/还原与输入输出是否可接受是两项不同义务。模型生成预算限制的是模型实际生成的文字，不能因复用同一个 `maxTokens` 字段就顺手变成引用展开后正文的硬上限。若没有独立的行为约束依据，接入只做表示转换，不附加估算、截断、重试或拒绝；删除门槛也不能偷偷换成另一种门槛。
- **适用**：compact、引用替换、序列化适配、解压/展开与原流程的最小侵入集成。

## 2026-09-17 — 已备好基础设施的接线不能重新扩成大工程

- **来源**：用户追问 compact 接入明明只有一两处调用，为什么耗时很长、产生许多外围改动。实际调用点只有两行准备、一行收尾，耗时却扩展到测试加载适配、源码/构建 SDK 类型混用和重复文档维护，且附带了后来被否定的预算策略。
- **原则**：调用处行数不代表总实现量，必须如实区分；但基础设施已就绪后的接入应只包含约定接线、旧重复代码移除和直接针对行为的必要回归。不得重新加入行为策略，也不得把辅助测试/文档/编排成本无界扩张。测试适配成本明显超过接线时应及时说明障碍并收敛最小边界，而不是以流程完备替代完成任务。
- **适用**：成熟基础设施的运行接入、小范围集成、测试环境适配与交付成本控制。

## 2026-09-17 — 引用不抛错不等于不回退或没有资源放大

- **来源**：用户要求 compact 引用接入自身不失败；独立 Hoare 推导和原生 preparation 探针确认，无效语法产生诊断，但合法空切片或终止符可使非空草稿展开为空，进入原有空摘要回退。重复短引用还可放大输出分配。
- **原则**：分别陈述语法不抛错、摘要有效性和资源条件。不能把返回一条非空提示冒充有效摘要来“修好”回退，也不能把生成长度当作展开内存上界。没有可达代码缺陷时不为制造改动而改；修正文档中的过期状态，并明确保留的语义与资源边界。
- **适用**：compact、引用替换、模板展开及带降级路径的数据变换。

## 2026-09-18 — 批量任务按约定保留部分效果，不套用事务默认值

- **来源**：用户明确修正批量创建方案：环边跳过但任务照常创建，被阻塞的启动请求只是不启动，并报告实际效果；终态依赖仍成功添加并说明已经满足。随后强调基础设施和运行接入必须分别批准。
- **原则**：批量语义由用户目标决定，不能默认整批回滚。尽力执行时先创建有效项，再按确定顺序处理依赖，最后尝试启动；逐项说明已生效与未生效部分，不将部分成功包装成全失败，也不将坏边静默丢弃。该容错不自动推广到单条操作或底层 I/O 故障。基础设施的实现授权不越过尚未批准的运行接口。
- **适用**：任务批量创建、依赖图更新、带部分成功结果的操作及分阶段插件接入。

## 2026-09-18 — 后台进度不能以空回应制造停工观感

- **来源**：任务基础设施子代理回报测试与接入方案进度后，主会话被唤醒显示 Thinking，却以空回应结束；用户无法判断是在继续、等待还是停工。
- **原则**：区分主会话回合结束与后台任务结束。在阶段性进度处简短交代实际剩余工作；用户追问时查一次真实运行状态，不以猜测解释停顿。必需实现和直接检查完成后立即收敛交付，不为整理报告追加测试或审查。
- **适用**：异步子代理、后台实现与分阶段交付。

## 2026-09-18 — 任务异常隔离必须区分宿主路径与提交阶段

- **来源**：用户要求任务系统普通故障不能拖垮 harness；获授权的独立 Hoare 分析指出，原生工具与门禁已有异常兜底，但补全失败可污染后续请求链。实际 built Editor 隔离探针中，两次请求失败而 provider 只被调用一次；原生持久化探针也显示日志可能先变更后抛错。
- **原则**：以真实调用边界判断异常影响，不把 helper 抛错直接等同于 harness 崩溃，也不把宿主兜底当作插件已返回明确失败。补全必须在捕获范围内 await 委托请求，并验证失败后的下一次调用仍可运行；失败退路不得重用已失败依赖。任务失败保留旧控制器记录和编号预留，但原生日志是否写入须诚实报告；持久化前准备好安装副本，成功返回后只发布该副本，避免在提交之后再做可失败的复制或格式化；提交后展示失败不能宣称修改已回滚。内部解析器在调用方完整承接时可以继续抛错，不逐函数机械套 catch。
- **适用**：OMP 任务控制器、工具门禁、人工命令、补全回调及其未来运行接入。

## 2026-09-18 — 共享定义与会话执行关系必须分层

- **来源**：Loop 2.0 讨论中，用户区分了 global/workspace 中“可注册的任务定义”和当前 session 的 active 任务，并要求共享定义不得因读取而复制成 session item。
- **原则**：存储作用域、注册关系和执行状态是三个不同维度。共享层只保存可复用定义；session 通过显式注册持有引用及独立进度；`list` 展示当前 session 已启用执行，`available` 只查询尚可注册定义且不得产生副作用。共享权限必须由用户命令的结构边界授予，不能把 AI 提供的 `scope` 参数当成授权。
- **适用**：定时任务、订阅、共享模板、跨会话资源和任何“定义可共享但执行状态私有”的插件设计。

## 2026-09-18 — 隔离 smoke test 必须同时隔离状态根并重建真实模型上下文

- **来源**：Loop 2.0 用临时 Pi session 验证时，将 cwd、session dir、workspace/global store 和 locks 全部放入同一临时根；完整 JSONL 含任务 custom entries，但 Pi `buildSessionContext()` 重建结果不含隐藏任务和未注册共享定义。
- **原则**：真实宿主测试不能只换 session ID；所有持久化根和执行锁都要显式重定向，并在测试后整体删除。判断 AI 可见性不能以“内容是否存在于 transcript/JSONL”为准，必须使用宿主的 context builder 或等价的一手请求证据；custom entry 的可持久化与模型可见性是两个维度。
- **适用**：Pi 扩展 smoke test、session 状态、LLM 上下文隔离、临时 global/workspace 数据和测试清理。

## 2026-09-18 — 共享任务的取消、删除与强删必须分开

- **来源**：用户要求普通 stop 只取消自己的 registration，普通 delete 只能在没有其他注册者时删除共享定义，而用户 `delete --force` 可令全部注册失效；AI 不得 force。
- **原则**：取消改变当前 session 的执行关系；删除改变共享定义所有权；强删撤销所有 session 的共享执行资格，三者不能复用一个模糊操作。跨 session 强删应在共享索引中立即失效，并让离线 session 下次启动时清理本地引用，不能宣称原子改写其他 session JSONL。Catalog 不可读也不能被当作已强删，否则 reconciliation 会误删仍有效的本地状态。
- **适用**：共享定时任务、订阅关系、协作资源删除、离线客户端和跨会话权限撤销。

## 2026-09-18 — 接入后文档终态必须逐文件核读，不能采信实现者自述

- **来源**：Loop 2.0 转正提交后用户追问文档是否全部同步；实际发现 architecture/detailed-design 仍写着“future 自动补全未注册”、decisions.md 的 D6 与 non-decisions 已被推翻但未标注、旧 v1 设计文档无取代标注。这些内容曾被子代理自述为“已更新”。
- **原则**：委托实现后的交付清单里，“文档已同步”是一种主张而非证据；接入、删除、重构这类改变时态的动作会让文档中的 future/not wired/core-only 措辞整体翻转含义。核验必须亲自逐文件读终态，重点扫时态标记、决策状态和 superseded 标注；废弃决策按规范标注取代而非删除或改写。
- **适用**：委托实现后的文档验收、分阶段接入、方案转正、任何含“将来/未来/尚未”描写的文档交接。

## 2026-09-21 — 基础设施验收与行为接入必须是两个授权门

- **来源**：用户明确要求先完成 compaction 路径压缩基础设施并执行 Hoare 推理，但不得提交、不得接入当前行为；Impression 选模功能再次明确先实现纯基础设施并测试，接入须另经批准。
- **原则**：第一阶段只能落地未被运行入口引用的纯模块、直接源级测试和证明材料，并以入口未变及无新 import 说明现有行为未变。未来接入补丁可先列精确位置、动机和实际行数，但不能应用，也不能把配置及两处调用点的真实改动藏进“10 行计划”或拿基础设施测试代替接入后回归。第二阶段须重新授权后才改入口；若用户保留 reload/live 验收，不代为 reload 或调用真实 provider，分开交付离线通过与 live 待验。
- **适用**：分阶段 runtime 接入、provider/compaction 行为变更、feature flag 启用及任何“先构建后上线”的插件工作。

## 2026-09-21 — 组合任务动作只编排既有原子动作

- **来源**：`done + startNext` 设计中，用户要求直接复用现有 `start` 基础设施，并质疑非空数组、去重和独立启动逻辑是否必要。
- **原则**：便利型组合 action 只负责输入归一化、按序调用既有原子 action、汇总原子结果；不得复制其状态校验，也不得无依据新增非空、去重或事务规则。复合动作若保留主动作的部分效果，必须逐项返回后续动作错误，不能因主动作成功而静默吞掉 handoff 失败。
- **适用**：任务生命周期组合、批量快捷参数、已有原子状态转换之上的 API 编排。

## 2026-09-22 — 基础设施故障只报告任务影响

- **来源**：`startNext` 委派审查连续遇到 staged 验收条件和模型标识校验故障时，进度回复直接暴露了 `thinking`、模型 ID 和重试协议，用户无法判断这些术语与功能任务的关系。
- **原则**：面向用户报告执行基础设施故障时，先说明实际任务哪一步完成、哪一步未完成、代码是否受影响以及下一步；内部模型标签、调度字段和协议细节只有在需要用户选择配置或授权时才展开。自动重试不得形成无法理解的连续状态噪声，出现重复基础设施故障时应收敛或请求决策。
- **适用**：子代理、模型路由、验收 gate、后台任务与异步进度沟通。

## 2026-09-22 — 批次可行性不能由单项参数形状否定

- **来源**：用户暂缓继续扩展 done/expire，提出未来统一 add、依赖更新、逐项 reason 的 expire、done、start；此前讨论把共享 reason 的缺陷过度推广为批量 expire 不合理。
- **原则**：先区分批次必须保留的逐项信息与当前参数表示。逐项 reason 可以消除共享 reason 的问题，不能由旧形状直接否定批量能力；固定阶段批次只承诺该执行顺序，不冒充任意操作序列。讨论未来替代方案不等于授权继续实现。用户随后选择保留当前接口：组合能力的可实现性不证明扩展有必要；当现有快捷方式已覆盖实际需求，应优先保留可观察、易归因的操作粒度。批次增加组合表达力不等于获得绕过状态校验的权限，两者不可混称。
- **适用**：任务批次 API、生命周期组合、命令聚合及延期设计讨论。

## 2026-09-24 — 快速判定与摘要长度不能代替任务价值判断

- **来源**：用户指出 Impression 的 passthrough 判定过慢，并质疑“蒸馏结果比原文长就返回原文”的现行规则；提议调研 Jev 两阶段路线，而非直接改代码。
- **原则**：分离局部调用速度、整条处理链的端到端延迟，以及结果对下一步行动的价值。新增快速判定若每次都串行增加请求，只有省下的蒸馏工作覆盖额外调用时才更快；摘要字符数超过原文只能表明压缩量为负，不能推出它没有忠实、有用的综合判断。把速度和交付质量分别用真实任务样本衡量，再决定路由与长度策略。
- **适用**：Impression、模型路由、缓存/摘要回退及任何以额外分类调用替换生成步骤的流水线。

## 2026-09-24 — 速度实验必须区分可运行原型与真实服务测量

- **来源**：Jev 试验时缺真实凭据；后来用户授权用 `pi -e` 对 Luna/Sol 各跑三次相同合成任务，debug 显示同一 system 指令、工具结果与末尾任务，但外层 assistant 历史偶有一条额外文本，事件转录也没有蒸馏调用的 token/费用字段。
- **原则**：先确认真实凭据与隔离目录，再做可复现的真实调用；mock、导入成功或供应商标称值均不冒充实测。对模型 A/B 逐项核 system 指令、当前工具结果、末尾任务及历史消息，报告未控制的外层差异；从 debug 请求写入到工具结果交付的时间只称端到端近似延迟，不称纯服务端时延；转录没有蒸馏 usage 就不推算其价格。保留原始请求和会话事件供用户检查，但对外只给去敏摘要。
- **适用**：外部模型/服务的性能实验、插件副本试验及需要真实凭据的即时验证。

## 2026-09-24 — 推理等级先核对具体调用接口与 provider 参数

- **来源**：Impression 固定模型讨论中曾误判 `complete()` 不能附带 effort；后续用户要求 Luna 不附带档位并明确纠正“NULL 不是 LOW”。真实 debug 证实插件选项未设置、元数据为 null，而 Codex 官方适配器在 wire 请求中写 `reasoning.effort:"none"`。
- **原则**：分别核对配置层、插件传参层、provider 适配器与实际 wire 请求，不把某 provider 的选项说成跨 provider 通用，也不从“未显式传字段”推断接口不支持。用户指定的 effort 若可选或不适用，就保持空值；debug 应写 `null` 而非含混的 `default`，更不能称它为 `low`。只有实际请求体才能说明 provider 如何编码空值；它与外层模型独立的 thinking 档位不能混称。配置串仍须遵守会话覆盖与显式 `_SELF` 恢复语义。
- **适用**：Impression 的 `distillModel[:effort]` 配置、Pi 模型路由与跨 provider 参数接线。

## 2026-09-24 — 省略 provider 不等于限定当前 provider

- **来源**：Impression 固定蒸馏模型方案中，我把 `[provider/]model` 的省略项解释为只在当前 provider 查找；用户用 `glm-5.3` 反例纠正。隔离测试表明 TUI `fuzzyFilter` 排序不能凭直觉推断；接入测试中未限定 provider 的 `glm-5.3` 曾先命中未认证的 `opencode/glm-5.3`，而不是后来注册的 faux provider。
- **原则**：可选 provider 缺省表示跨目录找候选、当前 provider 优先，不是把检索限定到当前 provider。区分宿主 CLI 的单模型解析、TUI 导出的 `fuzzyFilter` 候选列表与 `ModelRegistry.find(provider,id)` 的精确查找；已有候选搜索直接复用，选择完整 `Model` 对象，不先压成 provider Set 后用模糊输入做精确 `find`。按真实 matcher 顺序测试“第一项”，并将目录命中与认证成功分开：若按用户规定取到未认证的首项，应明示目标并失败透传，不暗中换另一账号；要稳定账号由用户显式写 provider。
- **适用**：Impression 的 `distillModel`、具名 provider、多模型路由及省略 provider 的配置语义。

## 2026-09-24 — 原文召回与再次蒸馏须按用户目标分开

- **来源**：用户质疑 Impression 为 Recall 单设重蒸馏调用，并提出 `recall(id)` 直接返回原文、或把其结果送入通用钩子但保持原 ID。现有代码重蒸馏时已用 `createRecallToolResult(impression.id, note)` 保持原 ID；只有拟议的无特判通用钩子会造新 ID，而现有 `deliverFullContent` 会在钩子前清空原文并标为已交付。
- **原则**：先把“取回已保存的原文”“以新上下文再压缩”和“保持引用 ID 稳定”分开：当前实现已满足第三项，不能把拟议方案的故障当成当前故障。若只要原文，可直接用恢复的 `impressions` 索引，且阻止召回结果被再次压缩；若把再次压缩移进通用钩子，则在它决定透传前不得清空同 ID 的原文，还须保证某次调用终能交付原文。变更原有重蒸馏或一次性交付语义前须明确报告边界，未经确认不删功能。
- **适用**：Impression Recall、工具结果二次拦截、缓存原文恢复与递归压缩链。

## 2026-09-29 — 默认旧路径须在新依赖求值前短路

- **来源**：获授权的多位 `gpt-6-sol` 按旧 `HEAD` 契约审查 Impression 入口拆分；Prover 指出默认 `_SELF` 的新包装函数在选择器返回当前模型前就求值 `ctx.modelRegistry.getAll()`，而旧工具结果与 Recall 路径不读取模型目录。Judge 核对宿主对单 provider 的目录异常会 best-effort 跳过，未找到正常宿主确定失败反例，但全称等价证明在新增依赖处断链。
- **原则**：给旧行为增加可选机制时，把默认/关闭分支放在新增外部查询和副作用之前，不能只在下游 selector 内写 `_SELF` 守卫；JavaScript 实参求值已经发生。报告分别标明“旧新条件性控制流不同”“正常宿主下可观察回归已证实”和“测试通过”，不从其中一项越阶推出另一项。只有宿主调用合同及所有消费者闭合，才可宣称该边界等价；多 agent 一致或源码相似都不是保证。
- **适用**：Impression 模型路由、可选插件能力、默认兼容路径和行为等价审查。

## 2026-10-02 — omp-v2 node:test 套件可用 resolve hook 原生运行

- **来源**：为 task 工具结果渲染改造补测试时发现：omp-v2 测试全为 `node:test` 风格且源码用 `.js` 后缀导入 `.ts`，仓库无 tsx，vitest 跑 node:test 文件会因 "No test suite found" 判失败（node:test 在导入期自跑并隐藏错误详情）。
- **原则**：`.js`→`.ts` 映射可用一次性 `module.register` resolve hook（捕获 `ERR_MODULE_NOT_FOUND` 后改试 `.ts`）+ `node --experimental-strip-types --test` 原生运行，能拿到完整断言输出；测试断言 `Text.render(w)` 输出须先 `trimEnd()`（组件会补空格到全宽）。若某测试断言编码了旧设计契约（如"不得有 renderResult"），行为变更时应更新断言而非绕开。
- **适用**：omp-v2 及其他 my-plugins 插件的 node:test 套件本地运行、TUI 组件渲染断言。

## 2026-10-02 — 插件依赖仓库包时 dist/src 双源必须先对齐

- **来源**：Boulder 点击展开实现中，`@earendil-works/pi-tui` 的 `MouseRegion` 在安装版 pi 运行时存在、在仓库 `packages/tui/dist` 不存在（dist 过期），导致本地 node:test 运行时 SyntaxError、tsc 类型也缺 `handleMouse`/`TuiMouseEvent`。
- **原则**：my-plugins 引用 workspace 包的导出前，先核对三个解析源是否一致：安装版运行时（真实用户环境）、仓库 dist（node/tsc 默认解析）、仓库 src（最新代码）。dist 过期时不擅自 `npm run build`（未授权），用测试 resolve hook / tsconfig paths 把包钉到 src，与安装版对源；类型不匹配的既有代码走运行时等价的宽松收窄，不改行为只为过检。
- **适用**：my-plugins 插件开发、对 packages/* 新 API 的引用、本地测试环境与生产运行时差异。

## Loop 多脚本执行不承担依赖编排，自动唤醒不冒充用户

- **来源**：用户明确所有脚本默认全部运行，依赖由 AI 在 sh 中封装；随后将错误聚合明确为 And/Or 可选，并最终指定默认 Or，即任意脚本失败就唤醒。用户要求唤醒仿照 omp-v2 Boulder，具有特殊渲染并明确提示自动系统来源；每个脚本超时默认 1800 秒，None 为无限。
- **原则**：单项脚本失败不得阻止其他脚本，不新增依赖图或遇错停止策略。执行范围与结果聚合是独立语义：全部执行，失败谓词按 And（全失败）或 Or（任一失败，默认）聚合后按任务策略唤醒一次。自动事件使用专属 custom message 和 renderer，正文明确不是用户发言，不覆盖用户既有裁决；区分 UI/会话来源与模型 API 的角色，Pi custom message 最终转为 user，不能称其为真正的 system role。用户视觉摘要含唤醒 ID 与成功/总数，展开显示与 AI 相同的提示正文；结果块使用用户指定的 `<script="...", exit-code="...">` 形式，重点标记失败项，不另造内容副本或来源文案。
- **适用**：scheduled-wakeup 多脚本任务、失败聚合、系统唤醒消息与 Boulder 风格展示。

## 2026-10-28 — pi 扩展两条投递/订阅铁律（loop no-wake 实测教训）

- **来源**：实测发现 no-wake（triggerTurn:false）报告在 turn_end 边界被注入进行中的 run（session 文件中落在 toolResult 后 2ms）；第一版修复订阅了 `pi.events.on("agent_start")` 无效——那是跨扩展消息总线，不是生命周期事件。

## 2026-11-02 git 授权边界（loop-2 会话）
- 用户说"commit & push"只授权当次明确点名的改动；push 推到 origin 的内容必须是本次授权范围内的提交。一次 `git push` 把本地领先的**其他会话**的提交（a045b34b0、c70d46be4）一并带了出去——未被授权的内容不能随授权内容一起发布。push 前必须 `git log @{u}..HEAD --oneline` 逐条确认推送清单，含他人提交就停下来问。
