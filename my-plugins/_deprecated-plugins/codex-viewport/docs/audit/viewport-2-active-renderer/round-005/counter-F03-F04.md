### F03 — CONFIRMED

- `ManagedRenderer.render()` prepares a commit before building managed terminal content (`my-plugins/codex-viewport/managed-renderer.ts:72-128`). `prepareCommit()` invokes `component.render(width)` and saves that observation in both `PreparedCommit.lines` and `snapshotPreview` (`managed-renderer.ts:130-144`).
- Managed content invokes the same live component's `render(width)` again (`my-plugins/codex-viewport/managed-render-content.ts:10-21`). Those later bytes are used to construct the terminal frame and are written before acceptance (`managed-renderer.ts:100-120`).
- Acceptance validates ledger identity, revision, range, and item IDs, but does not compare `PreparedCommit.lines` with the bytes used for the terminal frame (`my-plugins/codex-viewport/transcript-ledger.ts:97-137,167-173`). `ManagedRenderer.acceptPrepared()` then records the preparation-time snapshot, not the terminal-frame observation (`managed-renderer.ts:130-152`).
- The mutation guard at `managed-renderer.ts:154-167` is later and narrower: it rerenders components already in `committedSnapshots`. It can detect a subsequent mismatch and force fallback, but it cannot undo the terminal write or ledger acceptance that already used differing observations.
- Therefore a synchronous stateful component can return `A` during preparation and `B` during managed-content construction. One transaction writes `B` while accepting and snapshotting `A`. No async interleaving or reentrant writer is required. Pi's `Component.render(width)` boundary supplies no purity or deterministic-output contract, so deterministic built-ins mitigate frequency but do not disprove the production invariant failure.
- Opaque finality remains heuristic: a pending opaque item finalizes when its first component ceases to be the chat tail (`my-plugins/codex-viewport/component-ledger-reconciler.ts:86-89`), and static classification uses constructor names. No inspected production caller or current test demonstrates wrong lifecycle binding for an otherwise deterministic component. That branch must not be presented as independently confirmed.

### F04 — DISPUTED

- Direct coordinator inconsistency is exact and reproducible from the implementation. A second `startRun()` outside `idle-native` or `entering-managed` calls fallback without detaching the current patch (`my-plugins/codex-viewport/runtime-coordinator.ts:49-54,216-219`). A second `finishRun()` during `draining-handoff` falls through to `idle-native` without necessarily clearing that patch (`runtime-coordinator.ts:118-152`). Calls after `shutdown()` mutate the nominally terminal `disposed` phase (`runtime-coordinator.ts:174-213`).
- The official caller trace disproves the ordinary duplicate-emission premise: there is one extension registration for each event, upstream event forwarding is awaited, low-level terminal branches are mutually exclusive, and accepted low-level operations are serialized. No production caller directly invokes repeated `startRun()` or repeated `finishRun()`.
- That serialization is not a complete disproval. `finishRun()` starts asynchronous drain and returns while the coordinator is `draining-handoff` (`runtime-coordinator.ts:118-151`). Awaited extension-event delivery waits for the handler, not for native drain completion. After the prior agent event settles, official `Agent` state permits a subsequent run. Its legitimate next `agent_start` can therefore call `startRun()` while the prior drain is still pending. `startRun()` treats that phase as fallback rather than waiting for or cancelling the drain. This is a production-shaped ordered `end → start` overlap, not a duplicate event.
- Current `runtime-coordinator.test.ts:12-63` covers normal handoff plus finish/shutdown during delayed entry, but it does not cover a successor `startRun()` during delayed drain, duplicate methods, or post-shutdown methods. Source inspection alone does not establish whether the stale drain callback always removes the patch quickly enough to prevent an observable native-phase/active-patch interval. F04 therefore remains **DISPUTED**, not confirmed as a persistent deployed failure and not rejected as unreachable.
- The resurrection subclaim is rejected. `shutdown()` cancels current entry, increments generation, clears prerequisites, recovers/disposes the owned patch, and assigns `disposed`; delayed activation additionally requires matching generation, phase, patch identity, and abort ownership (`runtime-coordinator.ts:55-101,169-213`). Official session teardown awaits `session_shutdown` before invalidation/disposal (`packages/coding-agent/src/core/agent-session-runtime.ts:167-172,395-400`). A direct post-shutdown phase mutation does not reactivate a disposed patch or restore cleared prerequisites.

### F04 runtime-test disposition

- **Reject as deployment evidence:** a test that merely calls `startRun()` twice, `finishRun()` twice, or invokes either after `shutdown()` proves coordinator non-totality but does not prove official production reachability.
- **Constructible production-shaped test:** delay native drain/DSR completion; perform one normal `capture → startRun → finishRun`; while phase is `draining-handoff`, deliver the next legitimate `agent_start` (or call `startRun()` as that handler does); assert phase, owned `doRender`, patch identity, terminal writers, and final state both before and after releasing the delayed drain. This decides whether the ordered successor-run overlap is transiently inconsistent, permanently strands the patch, or is safely recovered by the stale callback.
- **Constructible caller-contract test:** instrument extension `agent_start`/`agent_end` handlers during a transient provider failure followed by retry. Assert `start,end,start,end`, never `start,start` or `end,end`, while delaying the first drain. This combines the real retry caller with the coordinator overlap rather than relying on direct duplicate calls.
- No current runtime test pins either production-shaped case. Under the task's no-edit constraint, these tests were evaluated but not added.

## Final disposition

F03 survives the final counter-challenge because the accepting transaction demonstrably has no byte-equality invariant between preparation and terminal construction. F04 cannot be dismissed solely by exactly-once lifecycle emission: direct duplicate calls are not ordinarily reachable, disposal resurrection is blocked, but asynchronous drain allows a legitimate next run to enter before coordinator handoff settles. Until the delayed-drain successor-run test is executed, **F04 is DISPUTED**.
