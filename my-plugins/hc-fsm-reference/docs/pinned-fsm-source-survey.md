## Architecture

1. **Registration:** CLI parses typed YAML, substitutes registration-time path values and collects custody tree; capability-aware HTTP registration validates, persists and publishes the workflow. Forced registration additionally refreshes live actors with epoch/actor coordination.
2. **Host integration:** CC hooks or OpenCode plugin publish the host actor identity, acquire the frame early, gate actual native tools, and route actual Stop decisions. The tool namespace and normalized input keys are frontend responsibilities.
3. **MCP client:** stdio server publishes the 12 tools and one global control protocol. Each tool call gets its own HTTP client/connection. A transition prepares against the actor, runs hard checks, soft review window, then finish, then commits.
4. **Daemon:** per-session/agent actors own stack, definitions, variables, one-use readiness and Stop state. The single acquisition path restores persisted actors for tools and gates. Dispatch is session FIFO, applied to new actors before publication; it does not spawn host agents.
5. **Evidence/judges:** daemon-owned collectors produce bounded shared snapshots. Review/Stop/Watcher use typed semantic validators and the shared Claude/OpenCode driver; this is not the outer host's arbitrary model client.
6. **Watcher:** client-owned background scheduler discovers/reconciles roots, obtains snapshots/context, reuses judge sessions where safe, archives findings and delivers through frontend-specific transports with a delivery admission gate.
7. **Persistence/operator/UI:** SQLCipher-capable store holds authoritative governance data; separate run logging, read-only CLI views, actor graphs, static HTML and the OpenCode TUI provide supplementary observability.

## Residual risks and factual boundaries

- No runtime behavior, installed HC integration, provider availability, or test pass status was validated. This is a pinned-source inventory, not a review or acceptance run.
- HC support is conditional: the pinned product installer/backends name CC/OpenCode, and HC source was outside this task's investigation scope.
- Prompt guidance is not necessarily daemon enforcement: complete truthful liveness reporting, no parallel mutating FSM calls, and retaining fresh full state are cooperative-agent instructions. `submit_self_check` itself checks supplied booleans/target, not completeness of the YAML property set.
- Schema acceptance is not an implemented human approval path: `escalate` currently uses single review; `require_human_confirm` does not establish human-confirmation behavior.
- Store encryption protects the database at rest, not plaintext returned by tools or all materialized/transcript/log artifacts. Key conversion/upgrade guarantees require separate restart/failure evidence.
- Source comments and historical docs can describe superseded semantics. This report uses implementation over stale comments for live force refresh, required permission rule name, watcher opt-in and judge behavior.
- Child/Stop/watch evidence must be actor- and host-session-bound. Queue zero, terminal-state markers, or archive presence alone do not prove correct child ownership, frame release, actual Stop hook execution, or notification receipt.
