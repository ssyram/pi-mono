# CCA v5 全量分析：16 项 mismatch（疑 bug）人话清单

来源：`cca-fsmc-v5` 全量逐函数分析（2026-10-30 收官，828/828 覆盖，四硬门 PASS）。
分析结论的机器可读原档在 `~/cca-runs/cca-fsmc-v5/_cca_analysis/`（open-questions.md + 各 fn-*.md），
本文把它们翻译成人话，供决定"修哪些"。

**"mismatch" 是什么意思**：分析器逐函数对比"代码注释/调用方声明的意图"和"代码实际会做什么"，
两者打架且偏向是代码写错了，就标 mismatch。它是"高度怀疑的 bug"，不是"已确认事故"——
每一项下面都写清了什么时候才会真的炸。

**状态总览**：16 项 = 12 个独立 bug（有几项是同一个 bug 出现在两个文件）。
其中 **2 项已在 2026-10-30 当天顺手修掉**（见 ★），**1 项半修**（见 △），其余 9 个待你拍板。

## 一、已经修掉的（不用再管）

### 1. ★ 停机标记会炸整个回合（两个文件，同一类 bug）
- 位置：`owned-runtime.ts:152`、`hc-child-hooks.ts:67` 的 `markStopContinuation`
- 人话：stop 门禁拦下停机后要做个"标记这个会话转续跑"的小动作。代码写的是"查目录，查不到就算了"
  （`if (r)`），但用的查询函数**查不到会直接抛异常**，"算了"那个分支永远走不到。
  结果：只要传进来一个不在目录里的 id，整个回合收尾直接崩——今天下午你看到的
  `No Agent found for session main` 崩溃就是它。
- 状态：**已修**（commit `a045b34b0`：改用宽容查询 + root 停机传正确的 sessionId）。

## 二、真 bug，但触发条件苛刻（修不修看你对边角的耐心）

### 2. 启动器容量永久泄漏 → 最终所有子代理派不出去
- 位置：`src/children/root-launches.ts:76`（launch）与 `:85`（enqueue）
- 人话：派子代理有个"同时在启动中的数量上限"，进队列时 +1、启动完（finally）-1。
  但 **+1 发生在保护圈外面**：有两三条提前退出的路径绕过了 finally，计数只增不减。
  每绕一次就永久少一格容量，绕满之后所有新子代理永远排队——表现为"突然再也派不出 agent"。
- 触发条件：启动早期失败/提前返回（比如配置错、队列满时早退）才泄漏；正常启动不漏。
- 建议：修。一行搬进 try 的事，但属于"跑得越久越容易死"的慢性毒。

### 3. △ 会话统计读文件会"重复拼接"导致数据悄悄错掉
- 位置：`src/tui/fleet-stats.ts:56`（advance）
- 人话：fleet 面板的 token 统计靠增量读子代理的会话文件：记住上次读到哪（offset），
  只读新追加的字节。bug 在于：文件末尾**半行**（一行还没写完）会被留在缓冲区，
  但 offset 的推进和缓冲区的消费对不上——下一轮会把同一段字节再拼一次，
  轻则那行 JSON 解析失败被跳过（统计悄悄少算），重则 offset 越过文件长度后**永久读不进新数据**
  （面板上的 token 数永远停住）。分析器给的反例：先写 `abc` 再写 `def\n`，
  缓冲区会变成 `abcabcdef\n`。
- 状态：**半修**——我今天重写了这个文件的统计字段（美元/token 分开），但这条
  offset/缓冲区错位**还在**。它只影响面板显示数字，不影响任何投递/分析正确性。
- 建议：修（和 #2 同类慢性毒，且现在 fleet 面板天天在用）。

### 4. 会话启动失败一次，插件永久瘫痪（直到重启 pi）
- 位置：`src/extension.ts:13/15/39`（三个文件同一件事）
- 人话：插件启动失败时会装一扇"未就绪门"，把所有输入和工具调用拦住，本来是对的。
  bug 是这扇门**没有把手**：解除函数的返回值被扔了，而且门用的健康检查对象是个全新的、
  永远不会被标记为健康的实例。也就是说：**只要 session_start 失败过一次**（哪怕后来重进成功、
  新 runtime 已经建好），旧门还在原地拦一切。表现是"插件抽风一次后怎么都不响应，重启 pi 才好"。
- 触发条件：启动失败要真的发生（配置错、daemon 不在等）。
- 建议：修。这是"一次故障变永久故障"的典型，和今天修的 judge 挂死是同一危害级别。

### 5. 租约模块报错"货不对板"
- 位置：`src/coordination/canonical-lease.ts:31`（acquire）与 `:78`（release）
- 人话：这两个函数的调用方按约定"失败时抛自家协议错误（RuntimeError 家族）"来写后续处理，
  但文件系统出错时代码把**原始错误直接透传**了。就像合同写的退货运费到付，实际到付变现货到付款——
  调用方的分类处理逻辑遇到没见过的错误类型，行为未定义。
- 触发条件：磁盘/权限层面的 fs 错误（mkdir、stat 失败等），日常很少见。
- 建议：低优先级修（统一包一层 RuntimeError 就完事）。

### 6. Linux 下读宿主身份的边角错误也会裸奔
- 位置：`src/runtime/host-identity.ts:27`
- 人话：和 #5 同型——Linux 路径上读文件失败/被中断时，原生错误没包协议错误就跑出来了。
  macOS 主路径没这个问题。
- 建议：随 #5 一起顺手修。

## 三、"说好的功能其实不存在"型（多半是重构留下的残骸）

### 7. Read/Write/Edit 的 CC 别名整个是空壳
- 位置：`src/gates/file-tool-aliases.ts:90`
- 人话：模块注释说"把 OpenCode 风格的 Read/Write/Edit 工具名接到 pi 原生工具上"，
  代码把三个适配器都写好了，唯独**注册那一下从来没被调用**（`reg` 帮助函数定义完就扔了）。
  现状：有 agent 调 `Read`（大写）会直接"工具不存在"。
- 判断点：要弄清这功能还要不要——对偶剧本里如果 HC 侧有大写工具名调用，这就是真缺口；
  不要的话整文件删掉。
- 建议：先查剧本依赖，再决定补注册还是删文件。

### 8. 搜索别名只做了 1/3
- 位置：`src/gates/search-tool-aliases.ts:38`
- 人话：注释说注册 Grep/glob/LS 全家，实际只注册了 `glob` 一个，grep 和 ls 的适配器是死代码。
  另外注册的名字 `glob` 可能和 pi 原生工具撞名，撞了算谁的没查过。
- 建议：同 #7，先查剧本，再补齐或删。

### 9. 子代理事件推送整条线是死的（但有兜底所以没人发现）
- 位置：`src/children/native-child-coordinator.ts:224`（onEvent）
- 人话：设计上子会话的事件应该实时推给 fleet 界面（childEvents 订阅者），
  但事件泵的出口函数**全源码零调用点**——订阅者永远等不到回调。
  之所以没人发现，是因为 fleet 面板一直靠 1 秒轮询兜底（我们现在用的 vendor 状态条就是轮询的）。
- 建议：二选一——要么把接线接上（事件驱动，省轮询），要么删掉死线承认轮询是唯一机制。

## 四、"行为没错但文档/契约骗人"型（改口径，不改代码）

### 10. inbox 镜像的失败处理和声明不符
- 位置：`src/subagents/hc-inbox-sidecar.ts:7`（recordInboxSidecar）
- 人话：投递消息时往旁边写一份镜像文件（inbox.jsonl）供观察用。两个调用方的文档都声称
  "同步写盘，写失败就中断投递"——实际代码是**后台随便写写，失败完全吞掉，永远不抛**。
  行为本身是良性的（镜像丢了只损观测），骗人的是文档：照着文档写的容错逻辑在防一个不存在的失败点。
- 建议：不改代码，把两侧 fn 文档/注释的口径改成"best-effort 镜像"。（CCA 原档也是这个裁决。）

### 11. 投递批处理注释描述的机制根本到不了
- 位置：`src/subagents/hc-nico-host.ts:81`（deliver）
- 人话：注释说"空闲期连发多条会攒成一批：首条开跑、其余作为 steering 搭车"（trailing merge）。
  实际因为第一条就把状态置成 busy，后面全走另一条路，**攒批的循环永远不会执行**——
  是死代码。行为上用户看不出差别（消息还是都送达了），又是注释撒谎。
- 建议：删死循环、改注释；或真做批处理。倾向前者。
