# SubAgent 交互设计：与执行后端无关

状态：停止推进，仅保留为讨论过程材料；全文及其中的默认建议均不是实施依据，也未获用户接受。用户最新指定以当前 `../haokun-code` 的 SubAgent 接口与真实 FSM 交互逐项提取一比一复刻要求；后续规格须来自该源码调查，不能沿用本稿自拟规则。

## 1. 本轮目的与边界

本稿回答：在 FSM 场景下，Main、SubAgent 与用户之间应如何交互，SubAgent 的哪些变化必须可见，什么才算等待、完成、取消或失联。

本轮分工来自用户最新纠正：子代理只调研事实；主线程完成实现无关设计；共同讨论确认后，再讨论执行后端如何适配。本稿不选择内部 API、进程模型、通信传输、存储格式或目录结构，不以某个框架现有能力限制需求。

本稿沿用 `../../../principles.md` 的根目的和核心准入要求；本轮明确增加无 TUI 可运行及可观察交互要求。旧架构、tmux 子计划和现行代码仅是历史设计与实现材料，不因已经存在就成为本稿必须保留的机制。本稿确认前不替换它们，也不授权修改实现。

### 1.1 已有用户要求：Q.I

- 官方 Pi 下保留 FSM 的准入、身份、工具黑白名单、状态迁移和软硬停止裁决，不把基础设施失败包装成成功。
- 只有允许的子代理能执行；必载扩展和门禁在首次任务前就绪，后代与恢复不能绕过。
- FSM 未退出仍有 active 责任；一次模型运行停下不等于该责任已经结束。停止审核未通过前，不提前 settled 或向 Main 发送最终结果。
- Main 能派遣、观察、发送消息、处理子代理求决策及控制其后续执行；子代理的实际活动和停止情况必须可见。
- 不删除运行目录、会话历史及交付证据。清理运行资源不能顺带抹掉记录。
- 没有 TUI 也能完成核心工作；界面是同一交互能力的可选呈现，不是运行前提。
- 暂定执行框架选型不等于行为设计已接受；本轮不讨论具体适配方案，不实现或另派审查。

### 1.2 设计使用的事实与经验：Q.A / Q.E

- FSM 会话状态、一次模型运行状态、执行载体是否仍可控制，是不同事实。它们可能同时表现为“FSM active、本轮已等待、载体暂不可用”。
- 用户实际观察到派遣偶发失败；失败原因未定位，不能据此认定配置复杂、消息协议有错或某个框架不可靠。
- 旧分析会话在成功 FSM 调用后，一次迁移超时约 300 秒，随后出现大量快速重复失败；初始化失败与已建立通道失效是不同情况。
- spinner、上下文增长、进程存活和界面显示 busy 都不能单独证明工作有推进。

这些材料支持明确交互与失败语义，不支持声称本设计已实现、后端必然稳定或所有超时原因已查明。

## 2. 三个概念与关联边界

| 概念 | 含义 | 不等同于 |
|---|---|---|
| 子会话 | 具有稳定身份、父归属、历史和 FSM 责任的交互对象 | 某个进程、窗口或一次模型调用 |
| 派工 | Main 交给子会话的一项委托，包含目标、已明确的输入和完成边界 | 一条消息、一个后端执行尝试 |
| 一轮运行 | 子会话从被激活到允许让出执行权的一段运行，可能包含工具与停止审核 | 整项委托已经完成 |

一个子会话可以先后承接多项派工；一项派工可以跨多轮运行、等待和恢复。实现是否创建多个后端运行尝试，不改变派工关联，也不抹掉先前尝试的失败。

**本稿默认建议：同一子会话同时至多有一项未结案派工。** 补充、纠正、决策回复均归入该派工；需要并行独立委托时另开子会话。这个限制用于避免消息和结果归属混乱，不禁止一个父会话派多个子会话。

对外必须能稳定关联子会话、派工与具体命令／消息。关联从请求发出时就可用于查找结果；标识格式及其如何与后端运行 ID 对应，留待适配设计。

知道某个 ID 不代表有管理权。派遣与管理都验证真实父归属及授予的管理范围，不跨根会话串用状态、消息或结果。

## 3. 状态：分别回答三个问题

状态查询必须同时回答以下问题，而不是只给一个 busy/done：

| 观察对象 | 对外必须能区分的事实 |
|---|---|
| 子会话可用性 | 可控制；暂不可控制／挂起及原因；已经关闭 |
| 当前派工进展 | 准备中、执行中、停止审核中、等待、正常完成、失败、取消；事实不足时明确未知 |
| FSM 责任 | 尚无活动 FSM；存在活动帧；本派工承担的帧已合法结束；暂不可确认 |

这是语义要求，不规定必须使用同名枚举或三个数据库字段。

具体约束：

- “可控制”不表示模型正在运行；“暂不可控制”不证明模型或工具已经停止。
- “等待”必须给原因、所等对象和如何继续，例如等 Main 回复、等异步工作、等用户处置或基础设施恢复。
- “失败／取消”不自动退出 FSM，也不把残留帧改成已结束；未完责任仍显示并报告 Main。
- “未知”不是成功、空闲或不存在，也不是重新派遣的许可。
- 状态附最近确认时间及事实来源类别；界面刷新和读状态不能伪造新的活动时间。
- 旧消息／事件不能把新派工状态覆盖成旧派工的完成结果。

## 4. 派遣与启动

### 4.1 派遣前

Main 提交委托时，应能明确目标、必要输入、执行范围及完成边界；可指定新子会话，或复用符合条件的已有子会话。没有额外机器可检查条件时，按普通执行完成语义交付，不能冒称结果已被独立证明正确。

若指定 FSM，应区分“进入目标 FSM 后工作”与“派工已预先建立目标帧”。子会话启动后先确认当前帧；已在该帧内就工作，不能重复 enter。

### 4.2 受理与就绪

派遣的可观察顺序：

`请求 → 准入通过并受理 → 准备 → 已就绪 → 开始执行`

- 准入失败时不开始任务，明确拒绝原因。
- 受理回执只表示委托已登记，不等于模型已运行。
- 身份、必载能力、门禁及所需 FSM 关联确认完成后，才可报告已就绪并执行任务。
- 准备失败时报告具体阶段，不把已有 ID、窗口或部分记录当成启动成功。
- 回执丢失时，调用方能按原关联查询；查询或恢复同一委托不能暗中再创建一项重复派工。
- 只有确认原任务尚未开始，或按原关联确认如何续接后，才可以重试启动；结果未知时不盲目重派。

### 4.3 等待结果

默认建议派遣先返回，Main 可继续处理其它工作；另提供等待结果的交互。两者的完成条件相同。

等待不能造成“Main 同步等子结果、子又等 Main 回复”的死锁：子发出求决策后，Main 的等待必须能让出控制权并呈现该请求。等待超时只结束这次等待，不自动取消子代理或宣称派工失败。

## 5. Main 与子会话的交互

下表描述能力，不规定最终工具名、函数签名或 CLI 语法。

| 发起方／操作 | 前提与即时回执 | 后续行为及边界 |
|---|---|---|
| Main：派遣 | 权限、范围及目标合法；返回受理／拒绝／结果未知 | 按第 4 节启动；不是只有一条“spawn 成功” |
| Main：列举／查看 | 验证管理范围；返回已确认状态或明确查询失败 | 展示未完、历史完成及异常记录；查询失败不能伪装空列表 |
| Main：即时补充 | 指向当前派工；说明已受理、已排队或被拒绝 | 在允许的运行边界交给原子会话；不撤销已执行副作用 |
| Main：下一轮补充 | 指向当前派工；说明排队结果 | 在当前一轮结束后的允许边界处理，不插入正在执行的工具中 |
| Main：回复决策 | 对应一个未解决请求；验证请求与派工关联 | 继续原委托，不误唤醒另一会话，也不默认扩大权限 |
| Main：请求停止／取消 | 指明对象与意图；立即区分已受理、被拒绝、结果未知 | 实际效果另行确认；详见第 8 节 |
| Main：恢复 | 核对原身份、历史、未完责任及当前策略 | 续接原委托，保留旧尝试错误；不借恢复重新派一个无关联 worker |
| 子：进度更新 | 归属明确，说明真实活动或阶段结果 | 不表示完成，也不凭更新文字推进 FSM |
| 子：求决策 | 给出具体问题、所需回复和当前阻塞原因 | Main 能回复或上提用户；无回复不等于获准 |
| 子：阶段交付 | 标明属于哪项委托、哪些部分已完成／尚未完成 | 可以供 Main 使用，但不能投影成整项委托完成 |
| 子：最终交付 | 满足第 7 节的结案条件 | 结果可取、关联准确，然后发布结案变化 |
| 子／控制方：故障报告 | 给出已确认阶段、原因及未知范围 | 暴露未完责任和下一可行动作，不静默换成成功 |

消息已接受、已排队、已交给子会话、已被运行消费，是不同阶段。只知道前一阶段时，不承诺后一阶段。

迟到的补充或决策回复不得悄悄落入下一项派工。已完成派工上的新要求，应明确成为新派工；失败或取消后的续作，应明确是恢复哪项原委托，保留此前结果。

## 6. 等待与通知

等待是正常交互状态，但不能只写“等着”：必须能看到所等事件、负责回应方及继续入口。模型无需为了维持等待而不断调用状态工具。

本稿建议的默认通知策略：

- 就绪失败、求决策、进入需 Main 处置的阻塞、最终结果及异常中断，主动通知真实派遣者。
- 常规进度和活动更新只更新可观察状态；不因每条进度都唤醒 Main 的模型。
- 已请求的阶段交付可以主动通知；它与最终交付明确区分。
- 通知按派工关联，可辨认重复；重连不能把历史结果当成新完成反复唤醒。
- 通知暂未投递不等于任务未发生或已经成功交付；状态和结果仍可主动查询。
- 嵌套派遣将求决策和结果送给真实父会话；父不可达时保留待处理事实并显示不可达，不默默改送另一会话。

停止审核未通过时，可以报告进度或故障；禁止的是提前宣告 settled／最终完成，而不是禁止所有子→父通信。

## 7. 停止审核与正常完成

### 7.1 一轮运行如何停止

`执行 → 候选停止 → FSM 停止裁决 → 继续执行，或合法让出执行权`

- 硬门、软审核及其证据仍由 FSM 规则决定；交互层不另设一套放行规则。
- 审核期间对外显示停止审核中，不能提前显示已停、空闲或完成。
- 被拒绝时继续当前运行，并保留拒绝原因；不能先向 Main 交付最终结果，再把子代理拉起来补做。
- 获准等待时可以让出本轮执行权，但派工状态是等待，FSM 责任仍按实际帧显示。
- 尚有排队消息或自动续行时，不把低层一次运行结束视为当前委托结案。

### 7.2 一项派工何时正常完成

正常完成同时要求：

1. 已到达该派工约定的完成边界，且当前没有仍须消费的续行指令、未解决的求决策或必需异步工作。
2. 相关停止裁决已经允许真正结束本轮执行，而不是处于审核或拒停续行中。
3. 本派工承担的 FSM 帧已按其流程合法结束；只有软门允许暂停但帧仍 active 时，不能因此认定整项委托完成。无活动 FSM 的普通派工不附加虚构的退出义务。
4. 结果及完成类别已有可恢复记录，Main 可以取回；然后才发布正常完成通知。

这里的“正常完成”证明约定的执行与结案边界已到达，不自动证明分析结论或代码语义正确。额外正确性条件必须来自该派工原先约定的要求，不默认追加审查。

## 8. 停止、取消与强制终止

这三种意图不能折叠成一个“stop 成功”。本稿提出以下默认语义，需在讨论中确认：

| 意图 | 交互结果 | FSM 责任 |
|---|---|---|
| 请求正常停止 | 请求按现行规则收尾；可能被门禁拒绝或转为等待 | 不绕过软硬门；只有正常结案才算完成 |
| 取消当前派工 | 显式撤回继续执行的委托；停止效果未确认前显示取消处理中 | 如仍有活动帧，明确保留未完状态并报告 Main，不伪造合法 exit |
| 强制终止执行载体 | 异常处置，明确告知可能有在途副作用；须观察实际终止或报告未知 | 不当作 FSM 批准或任务完成；记录可恢复点和未完责任 |

“命令已接受”“正在停止”“已观察停止”必须分开。载体终止不证明远端在途变更被撤销；取消也不回滚已经发生的文件或外部副作用。

强制终止不应由普通失败重试悄悄触发。哪些调用者可请求哪一种停止，由明确管理策略决定，不能仅凭子代理 ID 或缺少响应获得权限。

本稿不默认提供删除历史的清理能力。正常释放运行资源、取消和强制终止均保留证据。

## 9. 故障、超时与恢复

故障要回答：哪一步失败、已确认发生了什么、什么尚未知、下一步能做什么。

- 准入拒绝：未开始任务，不把它描述成 worker 崩溃。
- 准备失败：保留失败阶段；只有确认没有任务在执行，才可按原关联重新准备。
- 运行中的业务拒绝：保留具体门与原因；不把同一次拒绝无限重试，也不自动绕门或修改目标。
- 通信／执行能力失效：报告阻塞或不可确认状态；不能只让模型重复同一必败调用。是否中断当前模型运行是后续适配问题，不改变“不伪完成、不隐匿故障”的要求。
- 有副作用操作超时：标明已发送未确认或可确认未发送；不能从超时推出未生效。恢复先查实际状态，再决定如何继续，不盲目重放。
- 子执行载体退出：如实报告异常中断或退出，不能自动改成空闲／完成。
- 查询本身失败：返回失败及最近已确认信息的时间，不用空记录、旧 completed 或零活动掩盖。

恢复必须保留原会话、派工和 FSM 关联，重新确认当前权限与必载能力。如果原载体还在运行，不能再起第二个执行者；无法确认时报告未知，不拿重建假装已恢复。

恢复可以产生新的执行尝试，但旧尝试的错误和未知副作用仍可见。原派工若已正常完成，新工作不能覆盖其结果。

## 10. Main 生命周期与记录保留

Main 正常退出、重载、切换会话和崩溃是不同事件，但都不自动替子代理宣布完成。

本稿默认建议：用户结束父会话时，未完派工挂起并保留可恢复记录；重载不重复派工。具体执行载体如何暂停，留待适配讨论。

父崩溃后不承诺所有子执行者一定继续存活；必须保留最近可恢复记录，恢复时辨认仍在运行、已经中断和无法确认三种情况。不能仅因父不可达就删除子记录，也不能从历史状态猜当前存活。

父会话恢复后，Main 能列出未完责任及待处理请求，继续原派工；更换为新父会话需要显式确认归属，不把旧消息广播给同目录下其它会话。

子代理完成或取消后，释放资源与保留会话／派工历史是两件事。列表可以折叠历史、将活动项排在前面，但不能以隐藏代替删除，也不能只因历史记录存在就称执行者仍活着。

## 11. 无 TUI 与可观察性

以下能力在无 TUI 模式仍须完整成立：派遣与就绪、列举和查询、消息与决策回复、等待结果、停止／取消、恢复、结果取回及故障通知。

用户确认不能只能通过弹窗完成。需要人判时，应形成可查询、可回复的待决请求；没有回复时明确等待，不静默允许或卡在不可见窗口。外部如何提供这些调用入口，是后续适配设计。

有 TUI 时，界面消费同一状态和命令语义：

- 没有子会话时不显示无意义的常驻计数；有子会话时可见运行／等待／历史结果的基本情况。
- 活动及需处理项优先，完成历史仍可查看。
- 最近活动带真实时间；区分模型输出、工具活动、FSM 拒绝、审核和通信错误。
- 用量与时长有明确范围；未知不显示成零，历史累计不冒充当前派工用量。
- 点击、滚动、展开和关闭查看界面不改变任务生命周期，也不成为后台工作继续的必要条件。
- 只有派遣、消息、回复、停止等明确控制动作才能改变相应交互状态。

## 12. 关键交互轨迹

| 场景 | 必须观察到的轨迹 |
|---|---|
| 正常派工 | 请求 → 受理 → 准备 → 就绪 → 执行 → 审核允许 → 满足派工/FSM结案边界 → 结果可取 → 完成通知 |
| 已预入 FSM | 准备 → 确认已有正确帧 → 工作；不再 enter 同一帧 |
| 未预入 FSM | 准备 → 按委托进入目标帧并确认 → 工作；进入失败不报任务已正常启动 |
| 软门拒停 | 执行 → 停止审核 → 拒绝及原因 → 同一委托继续；中间无正常完成通知 |
| 合法等待 | 执行 → 裁决允许让出 → 等待及原因/FSM仍active → 对应消息到达 → 原委托继续 |
| 子向 Main 求决策 | 请求有明确关联 → Main收到需处理通知 → 回复关联请求 → 子继续；Main此前等待结果不阻挡回复 |
| 即时／下一轮补充 | 命令被接受或拒绝 → 按所选时机消费 → 影响原派工后续执行；不撤销已经完成的动作 |
| 派遣回执丢失 | 调用方查询原关联 → 找到原受理/运行事实，或明确未知；不是无条件新建 worker |
| 迁移超时 | 显示有副作用结果未知 → 查询真实FSM/工作状态 → 决定续接；无盲目重放和伪完成 |
| 取消／强制终止 | 明确意图 → 停止处理中 → 真实效果确认或未知 → 保留历史及未完FSM责任 |
| 父中断恢复 | 不宣布子完成 → 恢复时确认存活与归属 → 接管原工作或显示中断/未知，不产生重复执行 |
| 无 TUI | 上述同样成立，缺少界面不改变门禁、完成、等待和错误语义 |

这些轨迹是未来适配与直接功能测试的行为依据，不是本轮已经执行的测试记录。

## 13. 职责组合与关键不变量：P / M / R

这里只分配逻辑职责，不规定模块、类、进程或具体框架。

| 目标／性质 P | 责任分配 M | 组合理由 R |
|---|---|---|
| 未受控子代理不能执行 | 派遣控制负责身份、准入和就绪；FSM负责允许范围 | 任务执行必须发生在准入与门禁确认之后，不能由某个旁路直接触发 |
| 不提前完成 | FSM提供停止与帧事实；派工控制判断是否结案；结果交付保存与通知 | 本轮结束、FSM结束和派工结案分别判断，只有结案事实成立后才发正常完成 |
| 消息不串到其它工作 | 会话归属与派工关联贯穿命令、消息、状态及结果 | 不以“最近一个worker”或“同一目录”猜目标，迟到回复不能落入新派工 |
| 故障不变空转或伪成功 | 执行控制暴露可用性；FSM提供可确认状态；Main接收阻塞与未知事实 | 不把失联映成idle，不把未知当未发生，也不由模型盲重试替代恢复 |
| 无TUI仍能完整工作 | 所有控制和观察能力不依赖界面；界面只是调用与呈现 | 界面关闭或不存在不会消除消息、门禁、状态或结果入口 |
| 恢复不洗掉责任 | 会话与派工控制保留身份、历史、失败及FSM关联 | 重启载体或新尝试不创建无关联的新委托，也不删除旧责任 |

全程不变量：跨根隔离；就绪先于执行；停止裁决先于正常结束；结果可恢复先于完成通知；受理不等于执行；合法等待不等于完成；取消不伪造FSM退出；未知不投影为成功；恢复不重复已存在执行；清理运行资源不删除证据。

这里的论证说明职责如何共同满足设计要求，不证明某个尚未适配的实现已满足这些前提。

## 14. 本轮共同讨论的三个重点

以下是本稿具体默认建议，不写成用户已经接受的要求：

1. **每个子会话同时一项未结案派工**；补充和回复归入该派工，独立并发另开子会话。是否符合实际派遣习惯？
2. **停止意图分清正常收尾、取消派工、强制终止**；取消／强制终止可以结束实际执行，但残留FSM责任继续显示，不能当作合法完成。这三个动作应向哪些调用者开放？
3. **常规进度只更新观察状态，求决策、故障和结案主动通知 Main**；Main等待结果时能处理求决策，不为进度频繁唤醒模型。是否采用这一默认？

其余行为按现有要求推导；若讨论暴露真实冲突，修订对应行为和责任，而不是通过换后端绕过。用户确认本稿后，下一阶段才逐项讨论选定后端如何满足这些交互，哪些能力可直接复用，哪些需要适配，以及无法满足的具体缺口。
